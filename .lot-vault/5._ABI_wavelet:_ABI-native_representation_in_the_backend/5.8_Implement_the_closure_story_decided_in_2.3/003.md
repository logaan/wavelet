Concrete defunctionalization design, posted for review BEFORE implementation
per the 2.3 rider. It follows the decided shape (2.3 update 007, items 1-2)
exactly; the open design points from that decision (naming, boundary
diagnostic) are settled here.

**Arrow types.** An arrow type A = (T1 .. Tn) -> R with every Ti and R a
concrete WIT type. The checker grows a function type (Phase D) so Fn literals,
bare def references, and apply sites carry A statically; a Fn whose arrow type
cannot be made concrete is a static error under strict (this is exactly the
"function values" category of the 3.9 backlog, so landing this unblocks the
strict flip gate).

**Per arrow type A used in a component, the compiler generates:**

1. A variant with one case per function value of type A occurring in the file:
   - every `Fn` literal of type A (lambda-lifted to a top-level core function);
   - every top-level def of type A referenced as a bare value (zero-capture
     case) — this absorbs "qualified symbols as bare values" and untyped-def
     backlog items.
2. One dispatch function `dispatch(f: A-variant, a1: T1 .. an: Tn) -> R`: an
   integer branch table on the discriminant; each branch unpacks the case's
   captures and makes a direct call to the lifted function. Apply sites on a
   value of type A call the dispatch function. A single-case variant
   devirtualizes: the apply site compiles to a direct call and the variant is
   payload-only (captures), discriminant-free in codegen (its WIT form still
   names one case for 5.8.1 compatibility).

**Case payloads.** The captures of the Fn literal, concretely typed, as a
tuple in first-capture-occurrence order. Zero captures = payload-less case.

**Deterministic naming** (the design risk flagged in 2.3 update 003):
- Variant name: `fn-` + the WIT spelling of A with non-alphanumerics folded to
  `-`, e.g. `(u32, list<string>) -> string` => `fn-u32-list-string-to-string`.
  Injective enough in practice; a residual collision across distinct types is
  a compile error, not a silent merge.
- Case for a bare def `name`: `name` itself (stable across edits anywhere).
- Case for a Fn literal: `<owner>-<k>` where owner = the enclosing top-level
  def's name and k = the 1-based index of that Fn literal within owner's body
  in form-tree order. Stable under edits to OTHER defs; editing a def only
  renames its own lambdas' cases. Since first-cut variants never appear in
  synthesized WIT (see below), this stability matters for internal identity
  and for 5.8.1's future public form, not for today's WIT output.

**Boundary rule (first cut).** A function type in an Export/Import signature
is rejected with an explicit diagnostic: "function types cannot cross
component boundaries yet; import the combinator as a macro so it expands into
this component (see stdlib combinators), or wait for resource-lifting
(5.8.1)". Consequently no generated variant or dispatch function is ever part
of the synthesized WIT in the first cut — they are internal codegen artifacts.

**Oracle parity.** interp.rs's runner currently passes closures across
simulated component boundaries freely. The same rejection lands in
check.rs/wit.rs signature handling (shared by both engines), so oracle and
backend agree on exactly the governed programs. Interpreter closure SEMANTICS
are unchanged (defunctionalization is a pure representation choice; the
interpreter keeps its Value::Fn).

Implementation proceeds on this recorded shape after the layout/builtin work
it depends on (5.2-5.6); objections can land any time before then.
