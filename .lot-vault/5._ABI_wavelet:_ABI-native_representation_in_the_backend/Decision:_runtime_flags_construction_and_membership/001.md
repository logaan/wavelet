## 1. Context (verified against the current tree)

### The conformance requirement

The suite's `values` interface declares a flags type and a round-trip over it
(`conformance/wit/world.wit:92`, `:143`):

```wit
flags permissions { read, write, exec, admin }
permissions-rt: func(v: permissions) -> permissions;
```

The documented transform is a **flags complement — toggle every member**
(`conformance/suite/src/transform.rs:88`):

```rust
pub fn bump_permissions(v: Permissions) -> Permissions {
    v ^ Permissions::all()
}
```

The two rust seeds that drive the round-trip (`conformance/suite/src/seeds.rs`):
seed-a passes `Permissions::READ` (→ expected output `{write, exec, admin}`),
seed-b passes `Permissions::all()` (→ expected output `{}`, empty). So a faithful
callee must, given a runtime flags value, produce its complement over the four
declared members — inherently data-dependent, not a compile-time constant.

### What the wavelet callee currently writes

`conformance/wavelet/src/roundtrip-values.wlt` (the `permissions-rt` export):

```wavelet
Def permissions-rt Fn {v: permissions} The permissions
  flg(filter(Fn {n} not(contains(v n)) ["read" "write" "exec" "admin"]))
```

It expresses the complement as: keep the member names NOT already in `v`, then
`flg` that runtime `list<string>` into a `flags` value. This reads naturally but
uses two operations that DO NOT EXIST in the language:

- **`flg` is not a builtin.** It is absent from `src/builtins.rs::NAMES` (the big
  builtin list), so the interpreter never `env.define`s it; at runtime the symbol
  `flg` is unbound / not callable. (The `flg` string that appears elsewhere in
  `src/` — `src/macros.rs`, `src/meta.rs` — is the `wavelet:meta` FORM tag for a
  `Node::Flg`, i.e. the reflective representation of a flags *literal*, unrelated
  to a value constructor.)

- **`contains` is string-substring only** (`src/builtins.rs:575`):

  ```rust
  "contains" => {
      let mut a = args_n(arg, 2, name)?;
      let sub = want_str(a.pop().unwrap(), name)?;
      let s = want_str(a.pop().unwrap(), name)?;
      Ok(Value::Bool(s.contains(&sub)))
  }
  ```

  Both operands go through `want_str`, so `contains(v n)` with `v` a flags value
  traps in the oracle. There is no flags-membership builtin anywhere.

### Flags literals are STATIC syntax only

The only way to name a flags value today is a `{name name …}` literal (braces with
no colons), resolved in the reader to `Node::Flg(names)`
(`src/reader.rs:576-585`, `parse_braces`); empty `{}` → `Node::Flg(vec![])`
(`:537`). There is no runtime constructor. Docs: `docs/docs/language/values.mdx:25`
lists `{read write}`, `{}` as the flags value syntax.

### How flags behave in the oracle vs. the canonical ABI (the crux)

- **Oracle** — `Value::Flg(Vec<String>)` (`src/value.rs:18`) is an **ORDERED Vec**
  and its equality is **order-sensitive**: `(Flg(a), Flg(b)) => a == b`
  (`src/value.rs:117`). A flags-literal Match pattern is exact ordered equality:
  `Node::Flg(names) => matches!(v, Value::Flg(x) if x == names)`
  (`src/interp.rs:648`). The printer joins in stored order (`src/value.rs:297`).
  So in the oracle `{exec read}` ≠ `{read exec}`.

- **Canonical ABI** — a flags value lowers to a **bitset i32, declaration-ordered**
  (`src/emit.rs` `lower_flags` ~`:3770`: OR `1<<i` for each declared member
  present). Lifting decodes the bits back into a `TAG_FLG` box **in declaration
  order** (`lift_flags` ~`:4091`, "the names of the set bits, in declaration
  order"). The bitset is order-free.

- **The two already reconcile for static literals** by a rule you must preserve:
  a flags literal only goes canonical when it is a duplicate-free subsequence of
  the declared members IN DECLARATION ORDER (`flags_is_ordered_subseq`,
  `src/emit.rs:5465-5472`); a reordered or duplicated literal (`{exec read}`,
  `{read read}`) stays boxed, because lifting would rebuild it in declaration
  order and diverge from the oracle's source-order Vec. The backend also has a
  boxed `TAG_FLG` equality that matches the interpreter's Vec compare
  (`src/emit.rs:11025-11036`).

  **Consequence for any runtime constructor:** a `flg(list<string>)` must
  NORMALIZE its result to declaration order (and de-dup), or the oracle value
  (source/list order) and the ABI value (declaration order) will disagree and the
  differential harness will catch it. Normalizing requires knowing the declared
  member set + order — i.e. an expected/ascribed flags type at the construction
  site.

### The type-checker already permits the current text (block is runtime-only)

- `contains` types as `Bool` for ANY argument types
  (`src/check.rs` ~`:2358`: `"empty" | "contains" => Ok(Type::Bool)`), so the
  checker does NOT reject `contains(v n)`. Only the oracle traps.
- `flg(...)` is an unknown builtin → `check_builtin_call` default returns
  `Type::Unknown` (`src/check.rs` ~`:2455`), and the enclosing `The permissions …`
  ascription widens `Unknown` → `permissions`. So **type checking + WIT synthesis
  already succeed for all 35 exported functions** (confirmed by the session-16
  checkpoint). The gap is purely that `permissions-rt` has NO reference semantics:
  the oracle can't run it, so per "follow the oracle exactly" the backend can't
  faithfully lower it.
- The machinery to resolve a declared flags type from context already exists: a
  flags literal in an expected-flags context adopts the declaration's full member
  set and bit positions (`src/check.rs:1533`, `infer` for `Node::Flg` with an
  `expected` flags type). A `flg` builtin could reuse exactly this.

### Why this blocks the WHOLE callee

A WIT `values` export is all-or-nothing: WIT synthesis emits the entire interface,
and one un-lowerable export fails the whole component build. So this single
function keeps the whole values callee un-buildable and `test-values-callee.sh`
(the parallel of the passing `test-resources-callee.sh`) deferred.

## 2. The question

**What, if any, language surface should Wavelet grow so a `flags` value can be
constructed from and inspected against runtime data — enough to give
`permissions-rt` faithful oracle semantics and unblock the 5.12 values callee?**

Sub-questions any "add surface" answer must settle:

1. Does `flg` need an expected/ascribed flags type to resolve its member set and
   declaration order? (Per the crux above: yes, for normalization.)
2. What happens on an unknown member name (a string not declared by the type) —
   trap, or produce an `err`/skip? The oracle and backend must agree.
3. Membership: a new `flags-contains` builtin, or an overload of `contains`?
4. How does `Value::Flg`'s order-sensitive equality interact with runtime
   construction — normalize to declaration order at construct time?

---

## 3. Options

### (a) Add flags builtins: `flg(list<string>) -> flags` + flags membership

Grow two real builtins, oracle-first, then backend, then downstream surfaces.

**`flg` semantics (oracle, `src/builtins.rs`):** takes a `list<string>`, returns a
`Value::Flg`. To reconcile with the ABI it must normalize: resolve the declared
member set/order from the ascribed/expected flags type, keep only declared members
present in the input, and emit them in DECLARATION order (de-duped). Unknown member
name → the recommended behaviour is **trap** (matches how the interpreter treats
other domain violations, e.g. `to-char` on a non-scalar, and keeps oracle=backend
simple); an `err`-returning variant is possible but changes the result type to
`result<flags, _>` and complicates the callee. This needs the expected flags type
threaded to the builtin call — the checker's `expected`-type plumbing already
reaches `check_builtin_call`'s caller, but `flg`'s current path discards it, so a
small typing addition is required (give `flg` a real arm that returns the expected
flags type when present, else `Type::Unknown`).

**Membership:** either a new `flags-contains(flags string) -> bool` builtin (clean,
no overload machinery) OR overload the existing `contains` to dispatch on the first
argument's runtime tag (`Value::Flg` vs `Value::Str`). Overloading keeps the callee
text as-written and reads well, but `contains` is currently typed `Bool` for any
args, so the checker needs no change either way; the interpreter/backend just gain
a flags arm. A separate name is lower-risk (no behavioural change to existing
string `contains`).

**Backend (`src/emit.rs`):** `flg` lowers to the existing bitset construction — for
each input string, find its declared position and OR in `1<<i` (reuse the
`lower_flags`/`emit_list_contains` machinery at `:3770`); the result is canonical
by construction, so it sidesteps the order-sensitivity trap entirely on the backend
side. `flags-contains` lowers to a bit test (`(bitset >> i) & 1`) or, on the boxed
path, the existing `emit_list_contains` over the `TAG_FLG` box. Unknown-member trap
must match the oracle.

- **Pros:** the callee compiles as-written; the language gains a genuinely useful,
  general capability (data-driven flags construction/inspection) that any real
  program manipulating flags needs; the differential harness locks oracle=backend;
  reuses existing bitset + expected-type machinery.
- **Cons:** most work of the four options (oracle + backend + checker arm +
  membership + downstream docs/highlighting/LSP); introduces the first builtin
  whose result type is context-determined by an ascription (mild new precedent,
  though flags literals already do this); the unknown-member policy is a real
  design commitment (trap vs error value) that becomes part of the language.

### (b) Smaller surface: membership only; construct via Match over static literals

Add ONLY flags membership (a `contains`/`flags-contains` bool op), and express the
COMPLEMENT without a runtime constructor — by `Match`/`If eq` over the static flags
literals. **Important finding: the complement is very likely expressible with NO
new surface at all.** The only way to inspect a runtime flags value today is
Match/`eq` against static literals, and `permissions` has just 2^4 = 16 possible
values, so `permissions-rt` can be written as a Match mapping each declaration-order
literal to its complement literal, e.g.:

```wavelet
Def permissions-rt Fn {v: permissions} The permissions
  Match v [
    ({}                          {read write exec admin})
    ({read}                      {write exec admin})
    ({write}                     {read exec admin})
    ; … the remaining combinations …
    ({read write exec admin}     {})
  ]
```

This relies only on machinery that already exists and is verified: flags literals
(`Node::Flg`), order-sensitive flags-literal Match patterns (`src/interp.rs:648`),
the ABI lifting `v` into declaration order so declaration-order literal patterns
match (`lift_flags`), boxed `TAG_FLG` equality on the backend
(`src/emit.rs:11025`), and exhaustiveness satisfied by an irrefutable trailing
catch-all arm (`check_exhaustive` short-circuits on an irrefutable pattern,
`src/check.rs:2575`; a flags scrutinee otherwise stays gradual). The two tested
seeds (`{read}` and `{read write exec admin}`) MUST appear as arms.

- **Pros:** potentially unblocks the values callee with ZERO language change (or,
  with just a membership op, a much smaller filter-based form); no new construction
  semantics or unknown-member policy to design; smallest surface.
- **Cons:** the 16-arm Match is verbose and doesn't generalize past this one small
  flags type (a bigger flags type explodes combinatorially); it doesn't exercise a
  runtime flags CONSTRUCTOR, so 5.12's coverage of "build a flags value from data"
  is weaker than the suite's `v ^ all()` intent; **needs a build-verify** — I
  confirmed every ingredient exists but did NOT compile the 16-arm form end-to-end
  through the backend, so "Match on flags-literal patterns lowers correctly" is the
  one thing to check before committing (write it, run the callee vs both seeds).

### (c) Rewrite the conformance callee's `permissions-rt` to avoid runtime construction

Change the TEST, not the language: make the wavelet `permissions-rt` do something
that needs neither runtime construction nor membership — e.g. return a fixed
literal, or drop the true complement transform. This is distinct from (b): (b)
still implements the real complement (just verbosely); (c) abandons it.

- **Pros:** zero language work; unblocks the rest of the values callee immediately.
- **Cons:** directly weakens 5.12's coverage of the flags ABI — the whole point of
  `permissions-rt` is to round-trip a `flags` bitset through a data-dependent
  transform; a fixed/degenerate body still lowers a flags param+result but no
  longer tests data-driven flags behaviour. Also drifts the wavelet callee from the
  suite's documented transform (`v ^ all()`), which the file header currently
  promises it mirrors.

### (d) Defer flags-at-runtime entirely

Leave `permissions-rt` unbuilt and keep the whole values callee deferred (current
state), recording the lost coverage.

- **Pros:** no work; no premature language commitment.
- **Cons:** the entire values callee stays un-buildable and `test-values-callee.sh`
  stays deferred for one function — every other export (all scalars, char, string,
  records, tuples, variants, options, results, and all list functions via
  map/filter/fold) already compiles and is blocked only by the all-or-nothing
  export. That is a large, already-earned amount of conformance coverage left on
  the floor indefinitely.

### Recommendation

**Prefer (a), but FIRST spend ~30 minutes verifying (b)'s zero-surface path** (does
the 16-arm Match compile and pass both seeds through the backend?). If (b) builds,
it unblocks the values callee tonight with no language commitment, and (a) can be
added later as a proper feature on its own merits rather than under conformance
pressure. If (b) does NOT build (some gap in backend Match-on-flags), do (a) with a
separate `flags-contains` builtin (lower-risk than overloading `contains`) and a
`flg` that resolves its type from the ascription and **traps on undeclared member
names**. Avoid (c) — it hollows out exactly the ABI behaviour 5.12 exists to test.
Avoid (d) as a permanent answer — it strands a nearly-complete callee. One-line
answers I can act on: "verify (b), fall back to (a)", "do (a) with flags-contains",
"overload contains in (a)", "rewrite the test (c)", or "defer (d)".

### If (a) — add flags builtins

1. **Oracle.** Add `"flg"` (and, if separate, `"flags-contains"`) to
