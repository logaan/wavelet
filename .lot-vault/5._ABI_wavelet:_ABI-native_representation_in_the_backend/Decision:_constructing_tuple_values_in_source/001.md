# Decision: constructing tuple values in source

This is one of the two remaining blockers on the 5.12 conformance **values
callee** (the other, backend `drop`, is a plain oracle-following backend gap
being closed in the concurrent backend-coverage session). The flags question
that was thought to be the "last thing" turned out to be answerable with zero
surface (`lot:033ky5FRo5Up9Id5G6cTmr` option (b), verified); this Thing is the
real language question underneath.

**The gap in one line:** Wavelet has no way to construct a `tuple` VALUE from
computed data in source. Tuple *patterns* destructure fine, tuples cross
component boundaries fine, but nothing evaluates to a fresh tuple except the
`zip` builtin and `Quote`/`Quasi` — and none of those can express what the
conformance callee needs.

Everything below the fences was verified against the current main checkout on
2026-07-07 (file:line citations are from that tree; REPL transcripts are from a
`cargo build` of it). No code was changed writing this up.

---

## 1. Context (verified against the current tree)

### Parens are ONE node — a call in eval position, a tuple only under Quote

The reader gives `( … )` exactly one meaning: it builds a `Node::Tup`
(`src/form.rs:12-15`):

```rust
/// A parenthesized form `(a b c …)`: the single call/application/tuple node.
/// In evaluation position it is a call (head = items[0]); under `Quote` it is
/// a tuple value.
Tup(Vec<NodeId>),
```

`parse_parens` (`src/reader.rs:487-491`): `()` → `Tup[]`, `(a)` → `Tup[a]`,
`(a b)` → `Tup[a, b]`; an attached head `f(x y)` folds to `Tup[f, x, y]`
(`src/reader.rs:472-477`). There is no separate tuple node and no grouping form.

In evaluation position a `Tup` is a call, and `step_call` **requires the head to
be a name** (`src/interp.rs:117-138`):

```rust
let name = match arena.node(head) {
    Node::Sym(s) => s.clone(),
    Node::Qsym(a, n) => format!("{a}/{n}"),
    _ => return err("call head must be a name (use apply for a computed function)"),
};
…
None => return err(format!("unbound name `{name}` in call position")),
```

So `tup(1 "a")` looks up `tup`, finds nothing, and traps; and a bare `(1 "a")`
traps earlier because its head `1` is not a name. Verified:

```
> tup(1 "a")
error: eval error: unbound name `tup` in call position
> (1 "a")
error: eval error: call head must be a name (use apply for a computed function)
```

**`tup` is bound nowhere.** It is absent from `src/builtins.rs::NAMES` (so the
interpreter never defines it) and from `src/emit.rs`'s `BUILTINS` list
(`:6923-6969`). The `tup` string that appears in `src/emit.rs` (`TAG_TUP`,
`:5073`, `:9092`) and `src/builtins.rs:691` is the `form-kind` tag name for a
`Value::Tup`, i.e. reflection over the call/tuple node — not a constructor.

### Commas are whitespace — so a comma literal is already a call form

The lexer treats `,` exactly like a space (`src/lexer.rs:61`:
`' ' | '\t' | '\r' | '\n' | ',' => i += 1`). So `(1, "a")` reads as the same
`Tup[1, "a"]` as `(1 "a")` and traps identically:

```
> (1, "a")
error: eval error: call head must be a name (use apply for a computed function)
```

### The printer already prints tuples as `(1, "a")` — a reader/printer asymmetry

`print_value` renders `Value::Tup` with parens and strict commas
(`src/value.rs:283` → `write_value_seq(items, '(', ')', …)`, joining with `", "`
at `:289`); the printer's docstring calls this "Canonical WAVE text: strict
commas" (`src/printer.rs:3`). So the canonical text of a tuple value is exactly
`(1, "a")` — which, read back in eval position, is a *call*, not that tuple.
Wavelet's printed tuple form and its reader meaning already disagree.

### The oracle CAN hold tuple values — just not from a plain source form

`Value::Tup(Vec<Value>)` exists (`src/value.rs:15`) and is produced by:

- **argument bundling** — an internal call payload only (`src/interp.rs:143-149`:
  0 args → `Tup[]`, 1 → the value, ≥2 → a tuple);
- **boundary lift** — a `tuple<…>` param arrives as a `Value::Tup`
  (`src/emit.rs` lift paths, e.g. `:4172`), which is why tuple round-trips work
  as *inputs*;
- **`Quote` / `Quasi`** — `form_to_value` turns a quoted `Tup` form into a
  `Value::Tup` of its quoted children (`src/value.rs:185`, `src/interp.rs:443`,
  `:485`);
- **the `zip` builtin** — `zip` pairs two lists into a `list` of tuples
  (`src/builtins.rs:489`), verified:

  ```
  > zip([1 2] ["a" "b"])
  [(1, "a"), (2, "b")]
  ```

`zip` proves a builtin can already mint `Value::Tup` values that print as
tuples; there is simply no *general* constructor.

### Tuple TYPES are spelled as forms, `tuple(a b)` — not `tuple<…>`

In a signature a tuple type is written `tuple(u8 string bool)` — a `Tup` form
with head `tuple`, parsed by `Type::from_form` (`src/check.rs:129-157`,
`("tuple", elems) => Type::Tuple(…)`) and rendered to WIT `tuple<…>` by
`type_text` (`src/wit.rs:1453`). Writing `tuple<…>` in source is a read error
(the `<` is not a token):

```
> The tuple<u32 string> (1 "a")
read error: read error at byte 9: unexpected character '<'
```

### Quote/Quasi already type-check as tuples (a partial, real spelling)

The checker **blesses a quoted form where a tuple is expected**
(`src/check.rs:260-265`):

```rust
// the docs bless `Quote (1 2)` as the literal-tuple spelling …
(Tree, t @ Tuple(_)) | (t @ Tuple(_), Tree) => Some(t.clone()),
```

So the oracle already has a *literal* tuple spelling, and it type-checks:

```
> The tuple(u32 string) Quote (1 "a")
(1, "a")
```

And `Quasi` + `Unquote` can even build a tuple from **computed** values and
still type-check:

```
> The tuple(u32 string) Quasi (Unquote add(1 2) "x")
(3, "x")
```

Both work in the interpreter today. Their limits: `Quote` is literal-only (can't
call `wrap-u8` on a bound name); `Quasi` works but reads as meta/tree machinery,
not data construction, and (see below) the **backend does not lower either into
a canonical tuple**.

### The backend can represent a tuple value but cannot construct one

Boundary lift/lower for `tuple<…>` exist and pass (`src/emit.rs:3734`, `:4172`,
`:4584`; the caller-role `tuple-rt` differential check is green). `node_mem_ty`
even admits a tuple as a canonical layout (`src/emit.rs:5486`). But there is **no
constructor**: `tup`/`zip` are not in `BUILTINS`, and `mem_field_ok` has no
`WitTy::Tuple` arm, so it falls through to `_ => false` (`src/emit.rs:5437-5476`)
— a tuple can't even be a canonical variant/result/record *payload* built in
source. Prior goal-5 sessions' "tuples compile on the backend" claim referred to
the boundary and pattern paths; the construction side was never build-verified,
because the values callee never built (goal-5 update `lot:033kyXijRu9Vq9mLw2j4SV`).

### Tuple PATTERNS already work (the asymmetry that makes this odd)

Destructuring is complete: `Match v [((a b) …)]` binds element-wise in the
oracle (`src/interp.rs:662`, `:681`) and the backend (`pattern_mem_tup`,
`src/emit.rs:2820`, `:2901`, `:3020`). Docs: `pattern-matching.mdx:20`. So you
can take a tuple apart in source but not put one together.

### What the conformance callee actually needs

`conformance/wit/world.wit:133-135` declares three tuple round-trips; the wavelet
callee (`conformance/wavelet/src/roundtrip-values.wlt:180-194`) destructures and
**rebuilds from computed values**:

```wavelet
Def tuple-rt Fn {v: tuple(u8 string bool)} The tuple(u8 string bool)
  Match v [((n s b) tup(wrap-u8(n) bump-str(s) not(b)))]

Def tuple-nested-rt Fn {v: tuple(point list(u8))} The tuple(point list(u8))
  Match v [((p xs) tup(bump-point(p) map(wrap-u8 xs)))]

Def result-tuple-direction-rt Fn {v: result(tuple(u8 u8) direction)} …
  (ok(p)  ok(Match p [((a b) tup(wrap-u8(a) wrap-u8(b)))]))
```

Because the elements are `wrap-u8(n)` etc., `Quote` cannot express them — the
callee needs a form that **evaluates its arguments**. It already assumes a `tup`
builtin.

Because a WIT `values` export is all-or-nothing (one un-lowerable export fails
the whole component build), these three functions keep the entire values callee
un-buildable and `test-values-callee.sh` deferred.

### Prior recorded position on paren semantics (2.7 — settled)

The 2.7 decision "grouping and the meaning of `(a)`" (Thing
`lot:033ichoJaN3hdjhyPgjlVj`, now archived) asked whether `(a)` should stay a
zero-arg call or become transparent grouping. **Logan answered: "Leave it as a
zero argument call."** The recommendation it accepted keeps parens meaning
exactly one thing everywhere — `(a b …)` is `Tup[a, b, …]`, a call in eval
position — and explicitly rejects overloading paren syntax. Any option that
makes `( … )` sometimes mean "construct a tuple value" reopens that settled
decision and is in tension with it.

### Downstream drift already present

Docs already assert the feature exists: "a literal tuple **value** comes from
`Quote` (or a builtin)" (`evaluation.mdx:13`, `syntax.mdx:53`,
`pattern-matching.mdx:24`); `values.mdx:18` lists `("abc", 123)` as the tuple
value syntax (misleading — that's a call form in eval position); `roadmap.mdx:27`
marks backend tuples "✅ … including across component boundaries" (overclaims —
construction from source does not work). Whatever is decided, these should be
reconciled. This is arguably a hole in goal 4's "full WIT surface expressible"
claim: a program cannot return or build a tuple-typed value.

## 2. The question

**What should the source-level spelling be for constructing a `tuple` value from
(possibly computed) elements — enough to give the callee's `tuple-rt`,
`tuple-nested-rt` and `result-tuple-direction-rt` faithful semantics, and to
close the WIT-surface hole?**

Sub-questions any "add surface" answer must settle:

1. Does the constructor need the expected/ascribed tuple type, or can it infer
   the element types from its arguments? (Unlike flags, a tuple needs **no
   normalization** — it is positional, so construction order = ABI order. The
   element types fall straight out of the argument types.)
2. Arity: is a 1-tuple meaningful/spellable, and does a 0-tuple collide with the
   already-error `()`/unit story?
3. Does it reopen the settled 2.7 paren semantics?

---

## 3. Options

### (a) A `tup` variadic builtin: `tup(a b c) -> tuple<A, B, C>`  — RECOMMENDED

Add a real builtin `tup` that evaluates its arguments and returns a
`Value::Tup`; its result type is the tuple of the argument types. This is
exactly what the callee already writes.

**Oracle (`src/builtins.rs`).** Add `"tup"` to `NAMES`; in `call`, `tup` receives
the bundled argument (the existing calling convention already turns `tup(a b c)`
into a `Value::Tup[a,b,c]` payload via `bundle_args`, so `tup` is close to
`identity` on ≥2 args — but must also handle the 0/1-arg bundle shapes to give a
true 0-/1-tuple rather than the bundle's collapsed form). Simplest faithful
semantics: `tup` collects its raw argument *forms*' evaluated values into a
`Value::Tup` of exactly that arity (so `tup(x)` is a 1-tuple, `tup()` the empty
tuple), independent of the ≥2-only bundle collapse.

**Checker (`src/check.rs`).** Give `tup` an arm in `check_builtin_call`
(`:2269`); `arg_tys` is already computed at the top (`:2275-2278`), so the arm is
just `"tup" => Ok(Type::Tuple(arg_tys))`. No ascription needed — but `The
tuple(u8 string bool) …` still works and unifies element-wise (`:275-279`),
which the callee relies on.

**Backend (`src/emit.rs`).** Add `"tup"` to `BUILTINS` and lower it by
constructing the canonical tuple in place from its already-typed element
expressions (the machinery `node_mem_ty` (`:5486`) and the record/list canonical
constructors already provide the layout; tuple is the positional record case).
Add a `WitTy::Tuple` arm to `mem_field_ok` (`:5437`) — a tuple field is canonical
when every element expression is (mirroring the `Record` arm) — so a tuple can be
a variant/result payload (needed for `result-tuple-direction-rt`). Because a
tuple needs no normalization, this is strictly simpler than the record case (no
field-order hazard).

**`The` interaction.** With imported/declared tuple types, `The tuple(...) tup(…)`
ascribes and unifies element-wise; nothing special is needed because tuple
identity is structural, not nominal.

- **Pros:** the callee compiles as-written; closes the WIT-surface hole with a
  general, obvious constructor; symmetric with the working tuple *pattern*;
  needs no reader/lexer/grammar change and **does not touch the settled 2.7 paren
  semantics** (`tup` is an ordinary named head); trivial checker arm; reuses the
  canonical-record construction machinery; differential-harness lockable.
- **Cons:** most backend work of the options (constructor + `mem_field_ok` arm +
  tests); adds a builtin name to mirror into the three grammars' builtin lists
  and the LSP; the 0-/1-arg bundle-shape subtlety needs a deliberate choice so
  `tup(x)` is a genuine 1-tuple.

### (b) A dedicated literal syntax — e.g. WAVE-style `(1, "a")` or a new bracket

Make some parenthesised/bracketed form *evaluate* to a tuple of its elements.

- The natural WAVE spelling `(1, "a")` is a **non-starter**: commas are already
  whitespace (`src/lexer.rs:61`) and `( … )` is already the call form, so
  `(1, "a")` *is* `Tup[1, "a"]` and means "call `1`". Making it construct a tuple
  would require the reader to distinguish "call parens" from "tuple parens" — the
  exact context-sensitivity the **settled 2.7 decision rejected** ("leave `(a)` a
  zero-arg call"). It also collides with the printer, which emits `(1, "a")` for
  tuples but can't read it back.
- A *new* bracket (say `⟨…⟩` or a sigil-prefixed `#(…)`) avoids the call-form
  clash but means lexer + reader + `form.rs` node (or a reader desugaring to a
  `tup` head) + all three grammars (`docs/src/prism/wavelet.js`,
  `tooling/neovim/`, `tooling/vscode/`) + regen. It buys terser literals but,
  because it still must evaluate its elements to serve the callee, it is just
  option (a) with bespoke syntax instead of a name.
- **Pros:** literal tuples read tersely; symmetry with `[…]` lists and `{…}`
  records if a free bracket is chosen.
- **Cons:** the obvious spelling reopens/contradicts 2.7 and clashes with call
  forms and the printer; any safe spelling is a large multi-surface syntax change
  (lexer/reader/grammars/regen) for what a `tup` head does with none; homoiconic
  cost — a new bracket adds a node the meta layer and every form consumer must
  learn.

### (c) No new surface — tuples stay boundary-only

Accept that tuples are only *received* (patterns + lifted values), never
*constructed* in source. Express the callee's tuple functions some other way or
change the conformance expectation, and document the WIT-surface hole.

- The three callee functions have no faithful rewrite: each must *return* a
  `tuple<…>`, and there is no non-`tup` way to build one from computed values
  (`Quote` is literal-only; `zip` only makes 2-tuples-in-a-list; `Quasi` is
  option (d)). So (c) in practice means **dropping or degenerating** those three
  exports (return a fixed lifted-through value, or drop them from the callee),
  weakening 5.12's tuple coverage — and, because the export set is all-or-nothing,
  the WIT world would have to omit them too.
- **Pros:** zero language work.
- **Cons:** permanently strands tuple construction — a real WIT-surface hole
  (goal 4) — and hollows out the tuple ABI coverage 5.12 exists to test; the docs'
  existing "a literal tuple value comes from Quote or a builtin" and roadmap "✅"
  claims would have to be *walked back*, not just reconciled.

### (d) Reuse an existing form: `Quote` / `Quasi` ascribed to a tuple type

No new constructor — lean on what already type-checks (§1): `The tuple(…) Quote
(…)` for literals, `The tuple(…) Quasi (Unquote e …)` for computed elements. Both
run in the oracle today.

- **Pros:** the smallest "surface" (arguably zero new surface — it's already
  blessed by the checker and the docs); no new builtin name to propagate.
- **Cons:** `Quote` alone can't serve the callee (literal-only); the working
  computed form is `Quasi`+`Unquote`, which reads as macro/meta machinery, not
  data construction — every element wrapped in `Unquote`, e.g. `Quasi (Unquote
  wrap-u8(n) Unquote bump-str(s) Unquote not(b))` — ugly and error-prone. **And
  the backend does not lower `Quote`/`Quasi` into a canonical tuple** (the meta
  layer is expand-time; there is no runtime quasi-to-tuple lowering, and
  `mem_field_ok`/the tuple constructor gap from §1 is unchanged), so (d) needs the
  *same* backend work as (a) plus keeping the awkward spelling. It also leans the
  data language on the meta layer, conflating `tuple<…>` values with quoted form
  trees. Best read as documentation of the *current* partial capability, not the
  answer.

### Recommendation

**Option (a): add a `tup` variadic builtin, oracle-first.** It is what the
conformance callee already assumes, mirrors the tuple *pattern* that already
works, closes the goal-4 WIT-surface hole with a single obvious general
constructor, and — crucially — does not reopen the settled 2.7 paren decision or
touch the reader/lexer at all. (b) either contradicts 2.7 (comma form) or is
(a)-with-extra-syntax (new bracket); (c) strands a real capability and forces a
docs walk-back; (d) is the honest description of today's partial state but is
verbose, meta-flavoured, and needs (a)'s backend work anyway. One-line answers I
can act on: "do (a) `tup` builtin", "add a bracket literal (b)", "no surface,
document the hole (c)", or "just use Quasi (d)".

## 4. What to do once answered (per-option execution plan)

Cross-cutting rules for any option touching language behaviour: **oracle first**
(`src/interp.rs`/`src/builtins.rs` define the reference semantics; `src/emit.rs`
is validated against it and must agree on every program), then backend, then
downstream surfaces. Gates: `cargo test` (incl. the differential harness and
`tests/backend_tuples.rs`), the release conformance matrix, `CHANGELOG.md`
`## [Unreleased]`, docs prose, and `./scripts/regen-examples.sh` if any
*documented* example changes. Note: backend `drop` is being fixed separately in
the concurrent backend-coverage session, so once tuple construction lands, the
values callee has **no** remaining language gap and `test-values-callee.sh` can be
added (mirroring `test-resources-callee.sh`) and run vs both rust seeds. Work in
your own worktree/branch, commit as you go, open a PR when green — do not push to
main.

### If (a) — add a `tup` builtin

1. **Oracle.** Add `"tup"` to `src/builtins.rs::NAMES`; implement in `call` to
   return a `Value::Tup` of its evaluated arguments at exact arity (decide the
   0-/1-arg shape deliberately: `tup(x)` a genuine 1-tuple, `tup()` the empty
   tuple, independent of the ≥2-only `bundle_args` collapse — you may need `tup`
   to see its raw arg count, or to reconstruct arity from the bundle). Add
   interpreter unit tests including nested `tup(tup(1 2) 3)`.
2. **Checker.** Add `"tup" => Ok(Type::Tuple(arg_tys))` in `check_builtin_call`
   (`src/check.rs:2269`; `arg_tys` already computed). Confirm `The tuple(…) tup(…)`
   unifies element-wise (`:275-279`) for imported/declared tuple types.
3. **Backend.** Add `"tup"` to `BUILTINS` (`src/emit.rs:6923`); lower it to an
   in-place canonical tuple built from the typed element expressions (reuse the
   canonical-record constructor path — tuple is positional record). Add a
   `WitTy::Tuple` arm to `mem_field_ok` (`:5437`, mirror the `Record` arm) so a
   `tup(…)` is a valid canonical variant/result/record payload (needed for
   `result-tuple-direction-rt`). Extend `tests/backend_tuples.rs` with
   construction cases that fail against the current emitter and match the oracle.
4. **Differential harness.** Add a small program exercising `tup` (flat, nested,
   as a result payload) and confirm interpreter == compiled; drop any related
   SKIP entry.
5. **Values callee.** `roundtrip-values.wlt` now builds as-written; add
   `conformance/wavelet/.../test-values-callee.sh`, run `run-values()` vs rust-a
   AND rust-b, correct the file's STATUS header and `conformance/wavelet/README.md`
   (drop the tuple blocker; note `drop` if that session hasn't landed yet).
6. **Downstream.** Mirror the new builtin name into the three grammars' builtin
   lists (`docs/src/prism/wavelet.js`, `tooling/neovim/syntax/wavelet.vim` — it's
   the `logaan/wavelet.nvim` submodule: edit, commit+push there, bump the pointer
   here — and `tooling/vscode/`) and the LSP builtin set under `tooling/`. Add
   `tup` to the `docs/docs/stdlib.mdx` builtin tables; fix
   `docs/docs/language/values.mdx:18` and `evaluation.mdx`/`syntax.mdx` so "a
   literal tuple value comes from `Quote` or a builtin" reads as "`tup` (or
   `Quote`)"; update `roadmap.mdx:27` to reflect that construction now works.
   `CHANGELOG.md` `Added`. Run `./scripts/regen-examples.sh` if you add a
   documented tuple example.

### If (b) — a dedicated literal syntax

1. **Reject the comma form up front** (it reopens 2.7 and clashes with call forms
   and the printer). If Logan wants a *new bracket*: add the token in
   `src/lexer.rs`, a reader rule in `src/reader.rs` desugaring `⟨a b⟩` (or chosen
   delimiter) either to a new `form.rs` node or, preferably, to a `Tup[tup, …]`
   head so evaluation reuses option (a)'s `tup` machinery (do (a) steps 1-3 for
   the semantics regardless).
2. Mirror the new syntax into **all three grammars** and `regen-examples`; update
   `docs/docs/language/{syntax,values,reader-sugar}.mdx` and the LSP. Then callee +
   downstream as in (a) steps 4-6.

### If (c) — no new surface

1. No `src/` change. Rewrite or drop `tuple-rt`, `tuple-nested-rt`,
   `result-tuple-direction-rt` in `roundtrip-values.wlt` (and the matching WIT
   exports in `conformance/wit/world.wit`, since the world must match the callee)
   to something needing no construction; document in the file header and
   `conformance/wavelet/README.md` exactly what tuple coverage is lost.
2. **Walk back the docs' overclaims**: `values.mdx:18`, the "a literal tuple value
   comes from … a builtin" lines, and `roadmap.mdx:27`'s tuple ✅ must be corrected
   to say tuple *construction* is unsupported. No grammar/LSP change.

### If (d) — reuse Quote/Quasi

1. This still needs the backend to lower a runtime tuple, so do (a) step 3
   (constructor + `mem_field_ok`) but drive it from the `Quasi`/`Quote`
   type-directed path rather than a `tup` head. Rewrite the callee's three
   functions in the `The tuple(…) Quasi (Unquote e …)` form and build-verify.
2. Add the differential + callee + `test-values-callee.sh` as in (a) steps 4-5.
   Document the chosen spelling in `docs/docs/language/{evaluation,values}.mdx`
   (it is currently only half-documented). No new builtin name, so no grammar
   change; check the LSP still surfaces `Quasi`/`Unquote` correctly in this new
   data role.
