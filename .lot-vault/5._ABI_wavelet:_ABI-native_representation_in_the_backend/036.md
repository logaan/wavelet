--- FLAGS: option (b) VERIFIED, zero surface ---
permissions-rt = the flags complement `v ^ all()`, written as a Match over the
16 declaration-order flags literals, each result ascribed `The permissions`.
Why the ascription: `permissions` is IMPORTED (roundtrip:suite/types), so the
checker cannot resolve its member declaration (flags_members -> None,
check.rs:1533-1539); without it each `{...}` result infers its own narrow Flags
set and the arms fail to unify ("Match clauses have incompatible result types").
`The permissions` makes each arm's type Named("permissions") (check_the returns
the ascribed type), so they unify. Macro-head attachment makes
`(pattern The permissions {...})` read as a 2-element arm.
Verified: (i) interpreter oracle computes the complement correctly on the seeds
{read}->{write exec admin} and {read write exec admin}->{} (and others) — right
answers run clean, a deliberately wrong expected traps; (ii) the backend LOWERS
permissions-rt (standalone build passes type-check + codegen). `flg`/`contains`
are NOT needed. => decision option (b) is the answer; (a)/(c)/(d) unnecessary.

--- THE REAL BLOCKERS (both need new language surface; out of scope here) ---
1. TUPLE CONSTRUCTION. `tup(...)` has NO oracle semantics at all — the
   interpreter itself reports `unbound name tup in call position` (step_call:
   tup is not a special form, not in builtins NAMES, unbound) — and the backend
   has no tuple constructor (`tup`/`lst` are absent from emit BUILTINS;
   mem_field_ok returns false for WitTy::Tuple so a tuple can't even be a
   variant/result payload). Bare `(a b)` reads as a CALL form, not a tuple.
   There is no way to BUILD a tuple value in Wavelet source today (tuple
   PATTERNS already work). Blocks tuple-rt, tuple-nested-rt, and the ok side of
   result-tuple-direction-rt. This is the biggest surprise: prior sessions'
   claim that "tuples compile on the backend" was never actually build-verified;
   the whole file never built, so `tup(...)` was never exercised.
2. `drop`. An interpreter builtin (builtins.rs:746, returns unit) but ABSENT
   from the backend BUILTINS set -> "unknown function drop (wasm backend)". A
   no-result WIT function needs a unit-producing body the backend can lower;
   none exists in source (a stray cell-set happens to work but isn't faithful).
   Blocks no-result, no-params-no-result.
Also fixed along the way (source-level, no surface): `none()` (parenthesized) is
not lowered by the backend — only bare `none` is (the non-bare ctor path
whitelists only some|ok|err; ctor_parts, emit.rs:5286). Switched the two option
round-trips to bare `none`.

Empirically confirmed everything ELSE builds: with tup (3 exports) and drop
stubbed out, the full values world compiles — all scalars, char, string,
records, variants, enums, options, non-tuple results, FLAGS (permissions-rt),
and all list functions (map/filter/fold). So after a tuple constructor + backend
`drop` land, the callee is complete; test-values-callee.sh can then be added.
