# Keep compiled resource formatting opaque

The compiled runtime exposes a user resource's internal state when rendering a bare constructor result. The documented contract says resources print as opaque handles such as <r>.

Reproduction using the compiled eval_snippet API:

```wavelet
DefResource r {New: Fn {n: s64} cell-new({count: n values: [1 2]})}
r(4)
```

Observed compiled result: cell({count: 4, values: [1, 2]})
Expected documented result: <r>

Discovered while removing the interpreter as a runtime reference (commit a22a65e). A former test only exercised interpreter printing and therefore did not catch the compiled discrepancy. The structured-state acceptance test now calls a typed resource method and asserts count=4, so it continues testing construction/state without conflating this separate formatting bug. The interpreter is not the semantics authority: use the documented resource opacity contract and Component Model resource representation when fixing this.

Investigate how snippet/export type inference and to-string/rendering handle a local resource constructor's representation. Ensure the renderer sees the resource type/handle instead of traversing its cell/state payload. Preserve resource identity, borrowing, drop/lifetime behaviour and ordinary cell formatting.

Acceptance: the reproduction returns <r> through compiled native and browser REPL paths; nested resources where supported also stay opaque; ordinary cells still render according to their documented contract; constructing, calling and dropping resources continues to work. Add an independent expected-result compiled regression and update documentation only if its intended contract changes. This is a separate existing compiler bug, not part of the withdrawn map/fold macro migration.
