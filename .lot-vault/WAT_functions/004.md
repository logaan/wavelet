# WAT-bodied functions: impact assessment

Assessment only — no code changed. Based on reading `builtins.rs`, `interp.rs`,
`value.rs`, `check.rs`, `emit.rs` + the `src/emit/` submodules, `host.rs`,
`runner.rs`, `wasm.rs`, and the docs.

## Where the codebase stands (facts the assessment rests on)

- Every builtin currently has **four surfaces**: the interpreter implementation
  (`builtins.rs`, ~800 lines, 66 names + 4 set ops), a typed signature in the
  checker (`check.rs::check_builtin_call`, ~700 lines), a wasm lowering
  (`emit/builtins.rs` 1,964 lines + much of `emit/helpers.rs` 2,726 lines), and
  docs/LSP. Adding one builtin means touching all four.
- The wasm backend (`src/emit/`, ~14.8k lines) is as large as the rest of the
  compiler combined. Its helpers are literally hand-assembled wasm written as
  `wasm-encoder` builder calls in Rust — e.g. `case_h` in `helpers.rs:1465` is
  ~100 lines of `fx.op(I::...)` that would be ~25 readable lines of WAT.
- Backend value repr: tagged boxes in linear memory (bump arena, per-call
  reset, a persistent region + write barrier for resource state), **plus** the
  goal-5 work that is actively migrating slots to unboxed scalars
  (`Repr::Scalar`) and canonical-layout memory (`Repr::Mem`). The internal ABI
  is still moving.
- The interpreter is the semantics oracle. Natively, `wasmtime` is already a
  dependency (the `run` host). But the docs `<Playground>` runs the interpreter
  compiled to `wasm32-unknown-unknown` with **no wasm engine in it** — it never
  executes emitted code.
- `wat` is not currently in the dependency tree, but `wasmparser`/`wasm-encoder`
  (same wasm-tools project) are. Adding `wat::parse_str` is a one-line dep and
  philosophically consistent with the existing toolchain.
- The docs already frame builtins as an implicit `wavelet:std/core` import, so
  the swappable-stdlib goal is stated; WAT functions would be a mechanism for
  it, not the goal itself.

## Q1 — Would it shrink the core much?

**Retrospectively: modestly. Prospectively: yes, meaningfully.**

Sorting the 66 builtins by what could actually move into WAT:

- **WAT-friendly (~25–30):** the scalar family — `add/sub/mul/div/rem/neg/abs/
  min/max`, `eq/lt/le/gt/ge/not` on scalars, the `to-*` conversions. These map
  to a handful of wasm instructions each. But they are also the *cheapest*
  builtins today (the goal-5 scalar fast path already compiles them unboxed),
  so deleting them buys the least.
- **WAT-hostile, and they're where the mass is:**
  - `map/filter/fold/zip/apply` need the closure ABI (funcref table,
    `(env, payload) -> box`) — deeply coupled to the internal repr.
  - `upper/lower/to-string/split/join/str-cat` need string allocation and (for
    case mapping) Unicode tables. Nobody should write Unicode case tables in
    WAT. (Side-finding: `case_h` is ASCII-only while the interpreter uses
    Rust's full Unicode case mapping — `upper("straße")` likely diverges
    between backend and oracle *today*. Worth a separate look.)
  - `read/expand/gensym/form-kind/rec-key/rec-val` are meta-layer, tied to the
    form arena — not expressible in WAT at all.
  - `cell-*`/`set-*` are entangled with the persistent-region write barrier.
- The backend's *structural* machinery — patterns, `Match`, records, canonical
  ABI lift/lower, resources, componentization (`canonical.rs`, `mem.rs`,
  `pattern.rs`, `core_module.rs`, …) — exists to compile *Wavelet* functions
  and stays whatever happens to builtins. Don't expect `src/emit/` to shrink
  much.

Two things make the answer better than "not much":

1. **It caps future growth.** The real cost of the current design is the
   four-surface treadmill for every *new* function. With WAT functions, an
   entire class of future builtin requests (bit ops, wrapping arithmetic,
   float intrinsics, SIMD — see Q3) becomes library code with a declared WIT
   signature: no checker arm, no emit arm, no interpreter arm each time.
2. **A second, cheaper lever exists for the list/HOF layer.** `map`, `filter`,
   `fold`, `zip`, `reverse`, `concat`, `contains`… are expressible in *Wavelet
   itself* via recursion + `head`/`tail`/`push` (tail calls already compile to
   `return_call`). The `STDLIB_MACROS` mechanism in `builtins.rs` — `If`/`Do`
   are already Wavelet-authored source bundled into the compiler — is the
   precedent: a Wavelet-authored prelude would remove more per-function surface
   area for that family than WAT would, with zero new ABI. WAT is the right
   tool for the *instruction* layer; Wavelet is the right tool for the *list*
   layer; components are the right tool for the *collection/functor* layer.
   The irreducible core is then: allocation, closure application, string
   primitives, the meta ops, cells/resources.

Also note the stdlib-as-swappable-component vision has a hard boundary WAT
doesn't fix: **WIT has no function types**, so higher-order functions can never
cross a component boundary. `map` can be Wavelet-prelude code compiled *into*
each component, but it cannot live in an imported `wavelet:std/core@x.y.z`
component. The swappable unit is "prelude source" more than "component" for
that family.

## Q2 — Foot guns?

**Almost entirely determined by one design choice: what ABI do WAT bodies see?**

**(a) The boxed-heap ABI** (params/results are i32 box pointers into the shared
linear memory): maximum power, severe foot guns —

- Heap corruption: a stray store trashes the bump-allocator state, interned
  data segments (which start at offset 16, right after the canonical-ABI
  scratch area at 0..16), or other live boxes. No isolation inside a module.
- Tag-invariant violations: a WAT body returning a box whose tag doesn't match
  its declared WIT type silently poisons downstream code — and the goal-5
  typed paths *trust* declared types to unbox, so this breaks the fast path,
  not just the slow one.
- Arena-reset hazards: values that must survive a call have to go through the
  `persist` write barrier; a WAT author won't know that.
- **Repr ossification — the worst one.** Publishing the box layout as a user
  ABI freezes exactly the representation goal 5 is actively migrating away
  from (Scalar/Mem reprs). Every future repr improvement becomes a breaking
  change to user code.
- The oracle can't run it: the tree-walking interpreter has no boxes and no
  linear memory, so boxed-ABI WAT is *uninterpretable* — the one hard project
  rule ("the interpreter is the semantics oracle") breaks structurally.

**(b) A scalar-only ABI** (params/results limited to bool/char/ints/floats —
core i32/i64/f32/f64, no memory access, or own non-shared memory): mild foot
guns only —

- wasm validation catches type errors; core types line up 1:1 with the declared
  WIT scalar types, so the declared signature is actually *checkable* against
  the parsed body — better than trust.
- Remaining hazards are honest and bounded: `unreachable` traps (worse error
  messages than `EvalError` strings), infinite loops, wasm's nondeterminism
  corners (NaN payload bits). All present in any FFI story.
- Crucially, the oracle can execute it: marshal `Value::Int` → i64, run the
  body, marshal back.

**Foot guns independent of ABI:**

- **Oracle divergence** if the interpreter keeps parallel Rust implementations
  of what the backend takes from WAT. Then every stdlib function is a standing
  divergence risk — the thing the project's one hard rule exists to prevent.
  The interpreter must *execute* the same WAT (wasmtime natively; see Q4).
- **Surface syntax**: WAT is s-expressions but not WAVE — `i32.const`,
  `local.get $x`, `offset=8` don't lex as Wavelet tokens. Embedding WAT as a
  **string literal** keeps the reader, all three highlight grammars, and the
  LSP untouched (per CLAUDE.md, a lexer change ripples to five artifacts).
  Extending the reader to parse WAT natively would be a large tooling tax for
  cosmetic gain. `wat::parse_str` errors carry line/col that can be
  offset-mapped back into the `.wlt` file.
- **Checker blind spot**: bodies are opaque to `check.rs`. Under the scalar
  ABI this is fine (core validation ≅ the type check); under a compound ABI
  it's trust-based.

## Q3 — New powers?

**Yes — and one of them is glaring.**

- **Wavelet has no bitwise operations today.** No `and`/`or`/`xor`/shifts/
  rotates/`clz`/`popcnt`, no wrapping arithmetic (`add` traps on overflow via
  `checked_add`). Adding these as builtins means ~10+ names × four surfaces
  each. One WAT-function facility gets the *entire family* (plus saturating
  conversions, `copysign`, `sqrt`, future SIMD) as library code. This is the
  strongest concrete payoff.
- Numeric kernels: hash functions, PRNGs, checksums, fixed-point math — hot
  loops in native i64/f64 with no boxing.
- A real self-hosting path for the stdlib: scalar layer in WAT, list/HOF layer
  in Wavelet prelude, collections as functor components — matching the
  README's "swap out the standard library" promise.
- An FFI story at the instruction level without requiring users to set up a
  Rust/Zig toolchain to produce a component.
- Honest counterpoint: anything expressible as a *component* is already
  reachable via `Import` + `compose`, with better isolation. WAT functions'
  unique territory is intra-component, low-overhead, instruction-level code —
  and (if ever extended beyond scalars) code that can interact with closures,
  which components never can.

## Q4 — The proposed v0 (parse, don't compile; lean on wat2wasm libraries)

The proposal is sound and the toolchain fits:

- `wat::parse_str` (wasm-tools family, same project as the `wasm-encoder`/
  `wasmparser` already in tree) turns the body into binary at build time.
  Splicing a parsed function into the emitted module is a known
  wasmparser→wasm-encoder exercise (remap type/func indices); fiddly but
  well-trodden.
- **Interpreter/oracle**: natively, instantiate a tiny synthetic module per WAT
  function with wasmtime (already a dependency) and call it — the oracle then
  runs the *same bytes* the backend splices, so agreement is by construction.
- **Playground**: `wat` is pure Rust and compiles to `wasm32-unknown-unknown`,
  and the browser already has a wasm engine — `js_sys::WebAssembly` can
  instantiate the parsed module. So the docs playground can support WAT
  functions without bundling an interpreter like `wasmi`. (Native test suite
  and browser then use different engines — wasmtime vs V8 — but for scalar
  code that's within spec-determinism.)
- **Recommended v0 constraints**: scalar-only signatures; body as a string
  literal; no memory/table/global imports (pure functions over scalars);
  validate the parsed body's core type against the declared WIT signature at
  compile time. This sidesteps every severe foot gun in Q2(a) while delivering
  the whole Q3 bitwise/numeric payoff. Compound types can wait until the
  goal-5 `Repr::Mem`/canonical layouts stabilise — then v1 can pass compounds
  by canonical-layout pointer (reusing `mem.rs`) without ever exposing the
  boxed heap.

## Verdict

1. **Core shrinkage**: modest on today's code (the movable builtins are the
   small ones; the backend's structural machinery stays), but it *freezes the
   core's growth* — combined with a Wavelet-authored prelude for the list/HOF
   layer (the `If`/`Do` mechanism already proves this out), the long-term core
   contracts to: allocation, closure application, string/Unicode primitives,
   meta ops, cells/resources.
2. **Foot guns**: acceptable if and only if v0 is scalar-only with string-
   literal bodies. A boxed-heap ABI would be a serious mistake right now — it
   ossifies a representation that goal 5 is actively changing, and it breaks
   the interpreter-as-oracle rule structurally.
3. **Powers**: real and immediate — bitwise/wrapping/float intrinsics are a
   currently-unfillable gap, and this fills the whole family at once.
4. **The tax**: the oracle must execute WAT (wasmtime natively, browser
   WebAssembly API in the playground). Tractable for scalars; this constraint,
   more than anything in the emitter, is what should shape the ABI.

Side-finding worth its own Thing: `case_h` (wasm lowering of `upper`/`lower`)
is ASCII-only while the interpreter does full Unicode case mapping — a probable
existing backend/oracle divergence on non-ASCII input.
