DefResource sub-decision 2 SETTLED: self discipline.

Question: how does a method body receive the rep?

Decision: option 2b — a method's first parameter is spelled `self: counter`
(the field name must be `self`, the annotation must be the enclosing resource's
name), and in the body `self` is bound to THE REP DIRECTLY — the exact value
the constructor returned (a cell, for the counter).

  DefResource counter {
    new:   Fn {start: u32} cell-new(start)
    next:  Fn {self: counter} ...
    value: Fn {self: counter} cell-get(self)
  }

Reasoning: zero grammar change — parse_braces (src/reader.rs ~520) makes braces
either all `k: v` pairs or all bare names, so bare-self-plus-typed-params
(`Fn {self n: u32}`) does not parse, and special-casing the name `self` in the
reader would taint the one-rule brace grammar and ripple into the three syntax
highlighters. Under 2b the checker (where DefResource knowledge lives) enforces
the self field; the reader stays dumb. Semantically honest per the canonical
ABI: inside the implementing component a handle to your own resource IS the rep
(wit-bindgen hands Rust impls &CounterRep the same way); own/borrow wrapping
only materializes at the component boundary — "within the defining component,
the type `counter` denotes the rep" is the rule (feeds decision 3). Declared
arity matches call-site arity: `counter/next(c)` takes one arg, its Fn declares
one param. Sibling calls pass self straight through: `counter/value(self)`.

Rejected 2a (bare `self` first param): needs a reader special case for mixed
braces keyed on a magic name. Rejected 2c (implicit self, WIT-style): breaks
Fn's contract that the parameter braces describe exactly what the function
receives, and declared arity (0) diverges from call-site arity (1). Also
rejected: self as opaque handle + rep(self) intrinsic — ceremony with no
benefit inside the defining component.
