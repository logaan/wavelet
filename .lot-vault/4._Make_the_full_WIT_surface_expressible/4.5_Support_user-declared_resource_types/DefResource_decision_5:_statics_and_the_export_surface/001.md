# DefResource decision 5: statics and the export surface

# Decision 5: statics, and how a resource exports

Settled so far: DefResource form; `counter/sum(vs)` use-site spelling (1a);
methods take `self: counter` bound to the rep (2b).

Two halves, one note (they interlock at WIT synthesis).

## Half A — the `Static` marker

The suite's static: `sum: static func(values: list<u32>) -> counter;`, mangled
`[static]counter.sum` at the boundary. Called `counter/sum(vs)` in wavelet per
decision 1a — identical to a method call at the use site; the difference is
purely declaration-side (no self, no rep).

### Option 5a (recommended): explicit `Static` marker

```wavelet
DefResource counter {
  new:   Fn {start: u32} cell-new(start)
  next:  Fn {self: counter} ...
  value: Fn {self: counter} cell-get(self)
  sum:   Static Fn {values: list(u32)}
           counter/new(fold(values 0 wrapping-add))
}
```

Reads like the WIT (`static func`). `Static` is not a seventeenth special form
— it is a marker head meaningful only in DefResource member position, exactly
as WIT's `static` is a contextual keyword inside `resource`. The redundancy
buys **declaration-site error detection**, because the checker cross-checks
both directions:

- a `Static` member that declares `self: counter` is an error;
- a non-Static member (other than `new`/`drop`) that *lacks* `self: counter`
  is an error — "member must take self: counter or be marked Static".

So forgetting `self` on a method is caught where you wrote it, not at a call
site or (worse) at the boundary.

A static whose result type is `counter` returns a counter value — typically by
calling `counter/new(...)` as above; the boundary wraps it as an own handle,
same as the constructor.

### Option 5b: infer staticness from the absence of `self: counter`

Zero ceremony, and 100% inferable given decision 2b's explicit self spelling.
But silent: deleting or misspelling the self field quietly reclassifies a
method as a static, and the mistake surfaces as a confusing arity/type error at
every call site. No cross-check is possible because there is nothing to check
against.

**Recommendation: 5a.**

## Half B — the export surface

### Recommended: bare `Export counter` exports the whole resource

```wavelet
Export counter                                  // whole resource into `api`
Export {iface: "demo:app/counters" name: counter}  // or into a named interface
```

One `Export` of the resource's name exports the entire unit — constructor,
methods, statics, destructor — as a single WIT `resource` block. This is forced
by WIT anyway: a method cannot exist apart from its resource, so member-by-
member export is unexpressible; the declaration is the source of truth and the
export just places it. The record form controls interface placement exactly as
it does for functions.

An **unexported** DefResource is a purely internal resource — legal and useful
(precedent: the `set` resource can stay entirely inside the guest, as the
`count-distinct` example in the type-system docs shows).

The suite's free functions (`make-counter`, `bump-counter`, `take-counter`)
are *not* part of the resource: they are ordinary `Def`s using decision 3's
type spellings, exported individually as usual.

**Recommendation: bare-name exports the unit; record form for placement;
unexported = internal.**
