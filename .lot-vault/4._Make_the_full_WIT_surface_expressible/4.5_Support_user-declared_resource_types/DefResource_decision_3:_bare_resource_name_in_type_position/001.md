# Decision 3: what does `counter` mean in type position?

Settled so far: DefResource form (option 1); use-site `counter/new(5)` /
`counter/next(c)` (decision 1a); methods spell `self: counter` and bind the rep
(decision 2b, which fixed one corner already: *inside a method, `counter`
denotes the rep*).

**Question:** in a general type position — free-function params and results,
other Fn params, DefType payloads — what does bare `counter` mean, and how are
own/borrow spelled?

WIT's own reading of the same text, for reference: a bare resource name in
param or result position means `own<counter>` (ownership transfers, callee will
drop it); borrows are explicit `borrow<counter>`, param-position only (WIT
forbids returning or storing a borrow); methods take an implicit
`borrow<self>`. The conformance suite's free functions spell exactly this:

```wit
make-counter: func(start: u32) -> counter;          // own out
bump-counter: func(c: borrow<counter>) -> u32;      // borrow in
take-counter: func(c: counter) -> u32;              // own in (consumed)
```

## Option 3a (recommended): match WIT — bare = own, borrow explicit

```wavelet
Export make-counter
Def make-counter Fn {start: u32} counter/new(start)     // result counter = own

Export bump-counter
Def bump-counter Fn {c: borrow(counter)} Do [ counter/next(c) counter/value(c) ]

Export take-counter
Def take-counter Fn {c: counter} counter/value(c)       // param counter = own, consumed
```

`own(counter)` is also accepted as the explicit synonym for bare `counter`.
`own` and `borrow` are ordinary names in type-form position — no lexer change
(`_` set the precedent for type-position tokens), just type-form parsing.

Why: every other wavelet type position is WIT text 1:1 (`list(u32)`,
`option(point)`, ...) — you can transcribe a WIT signature into a Fn header
mechanically, and this keeps that property for resources. The docs teach WIT
anyway; diverging on the *default* reading of the same spelling would be a trap.

## Option 3b: bare name illegal — always write own(...) or borrow(...)

Maximally explicit, and ownership transfer is consequential enough that forcing
the author to say it has appeal. But it breaks WIT transcription (a copied WIT
signature would be a compile error), adds noise to every signature, and the
result position has no choice anyway (results are always own), so half the
explicitness is dead weight.

## Option 3c: bare = borrow ("the common case for params")

Silently *inverts* WIT's reading of identical text — a transcribed WIT
signature would change meaning. Rejected out of hand; listed for completeness.

## Folded-in semantics (part of 3a as recommended)

- **Own-consumption is modelled in the interpreter.** Passing a handle to an
  own-typed param invalidates the caller's handle; any later use traps —
  matching the canonical ABI's trap on a dropped handle. interp.rs is the
  semantics oracle, so this is checked there first; the backend gets it from
  the handle table at the boundary.
- **Borrow params never invalidate**, and the checker rejects a borrow in
  result position or inside a stored type (as WIT does).
- Inside the defining component (method bodies), `counter` stays the rep per
  decision 2b; own/borrow only exist at the boundary.

**Recommendation: 3a.**
