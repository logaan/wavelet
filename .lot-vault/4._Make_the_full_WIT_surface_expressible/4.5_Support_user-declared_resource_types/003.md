Everything else in goal 4 landed (4.1-4.4, 4.6 spelling, 4.7 on branch goal-4-wit-surface), so this is the one child with a genuine undecided surface: **how is a user resource declared in wavelet source?** Unlike 4.6.1 there is no decision note for this, and it shapes the language, so posting the question before implementing.

**Question: what is the source spelling for a program-implemented resource type (the suite's counter: constructor, methods, a static, own/borrow free functions)?**

Options:

1. **A dedicated `DefResource` form owning the whole surface (recommended).**
   ```
   DefResource counter {
     new:   Fn {start: u32} cell-new(start)            // constructor -> the rep
     next:  Fn {self} ...                              // method (self = the rep)
     value: Fn {self} cell-get(self)
     sum:   Static Fn {cs: list(borrow(counter))} ...  // static
   }
   ```
   One declaration maps 1:1 onto WIT's `resource counter { constructor(...); next: func() -> u32; sum: static func(...); }`, so synthesis is direct and the checker knows exactly which functions are methods (self receives the rep). The rep is an ordinary wavelet value the constructor returns — mutable state is spelled with the existing `cell`, which the counter genuinely needs. This is also the shape the `set` functor's emitted resource already has internally, so the backend machinery (resource-new/rep/drop intrinsics, method routing) generalizes rather than duplicates.

2. **Grow `DefType`** (`DefType counter Resource {...}` or a marker field). Fewer top-level forms, but a resource is not a data type: it has behaviour and identity, its "fields" are hidden rep rather than a public record, and overloading DefType's payload shapes (record/list/flags/alias, all data) with a behavioural kind muddies both the form and the checker's TypeDef table.

3. **Convention-based export grouping** — ordinary `Def`s plus an `Export {resource: counter constructor: new methods: [next value] statics: [sum]}` record. No new declaration form, but the resource's shape lives at the export site rather than the definition, breaks the "declaration is the source of truth" pattern every other type follows, and leaves the interpreter with no single place to learn the method/self discipline.

Sub-questions the recommendation folds in: `own(counter)`/`borrow(counter)` become type-form spellings (they already exist as WIT text in the backend, and `_` set the precedent for lexing type-position tokens — no lexer change needed since own/borrow are ordinary names); resource equality is identity (handles), matching the interpreter's cell semantics; drop runs the destructor if one is declared, else no-op, matching the set resource.

Recommendation: **option 1**. Interpreter first: a `DefResource` binds `counter` (constructor), `counter/next`-style qualified methods (or bare method names? — I'd bind methods only through the handle-taking functions to match how imported resources read: `next(c)`), with handles as opaque identity values; then WIT synthesis; the backend half (exported-resource intrinsics beyond `set`) can ride goal 5's representation work if it doesn't fit sooner. Awaiting your call before implementing.
