# DefResource decision 4: destructor spelling and semantics

# Decision 4: the destructor

Settled so far: DefResource form; `counter/new(5)` use-site spelling (1a);
`self: counter` binds the rep (2b).

**Question:** how is a user resource's destructor declared, and what are its
semantics?

Component-model facts framing this: a resource *may* have a destructor; the
implementing component exports it as `[dtor]counter`; the runtime calls it when
an **own** handle is dropped (by the host, or by a guest that owns it); borrows
never trigger it; it runs at most once. The built-in `set` resource ships an
implicit destructor that just frees the rep — that is the existing behaviour to
generalize.

## Option 4a (recommended): reserved member name `drop`

```wavelet
DefResource counter {
  new:   Fn {start: u32} cell-new(start)
  next:  Fn {self: counter} ...
  drop:  Fn {self: counter} log("counter freed")   // optional destructor
}
```

The declaration already uses one reserved member name: `new` is the
constructor (decision 1a — WIT synthesis turns the `new` field into the
anonymous `constructor(...)`). `drop` extends the same convention
symmetrically: presence of a `drop` field synthesizes the WIT destructor.
Checker rules: `drop` takes exactly `self: counter` (no extra params) and its
result is unit. It is not callable as `counter/drop(c)` from user code — the
runtime owns when it fires (letting user code call it would create double-run
hazards the component model doesn't have).

Reserved member names after this decision: `new`, `drop`.

## Option 4b: a marker form

```wavelet
finalize: Destructor Fn {self: counter} ...
```

Introduces a *second* mechanism (marker head) alongside the reserved-name
convention already chosen for the constructor. Two mechanisms for the two
special members is worse than one; and unlike statics (where WIT itself writes
`static`), WIT has no destructor keyword to mirror — the dtor is anonymous in
WIT too, which fits a fixed name better than a marker.

## Option 4c: no user destructors yet

Absent-destructor behaviour only: dropping the last own handle frees the rep
(Rc drop in the interpreter; rep memory freed in the backend) and runs no user
code — exactly what the `set` resource does today. The conformance counter
needs no destructor, so this is sufficient for 4.5's acceptance test.

This is really a *staging* choice, not a design: even if implementation defers,
the spelling should be settled now so nothing lands that conflicts with it.

## Semantics (apply to whichever spelling wins)

- Absent destructor = no-op (rep still freed). Matches `set`.
- Runs exactly once, when the last own handle is dropped; never for borrows.
- Body receives `self` = the rep (decision 2b discipline).
- After it runs the handle is dead; any use traps (same rule as
  own-consumption in decision 3).

**Recommendation: 4a — reserved `drop` member — with 4c's staging note:
implementation of user destructor bodies may trail the rest of DefResource,
since the acceptance counter doesn't exercise one, but the name is reserved
and the checker rules land with the form.**
