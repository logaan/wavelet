# DefResource decision 6: identity equality and to-string

# Decision 6: observable semantics — two quick confirmations

Settled so far: DefResource; `counter/new(5)` (1a); `self: counter` = rep (2b).
These two are yes/no confirmations; both recommendations are chosen so that
interpreter/backend parity (interp.rs is the oracle) is trivially achievable.

## (a) Equality is identity

Two counter values are equal iff they are the same instance:

```wavelet
Let {a: counter/new(5) b: counter/new(5)}
  ...   // a = a is true; a = b is false, even though both "hold 5"
```

This matches component-model handle semantics (handles are capabilities, not
data) and the interpreter's existing cell identity (Value::Cell is an Rc; two
cells holding equal contents are distinct). Structural equality is meaningless
for a resource — the rep is hidden and mutable. Consequence: `Derive {Eq}` (or
Ord/Hash/Show) over a resource type is a compile error; identity equality is
inherent, not derived.

**Recommendation: yes — identity.**

## (b) to-string prints an opaque token

`to-string(v)` promises canonical WAVE text, but WAVE has no resource-handle
syntax, so a resource cannot round-trip. The value printer already has an
opaque convention: closures and case constructors print angle-bracket tokens
(`<constructor name>` etc., src/value.rs ~265) and are rejected from
form-serialization ("this value cannot appear in code"). Resources follow that
convention:

- `to-string(c)` prints **`<counter>`** — the angle-bracket token carrying the
  resource's type name, nothing else.
- Resources are not form-serializable (same error as closures/cells), and
  `read` cannot produce one.

Rejected alternatives:

- **Print the rep** (`counter(cell(5))`, the way bare cells print as
  `cell(v)`): leaks the hidden rep — the whole point of a resource is that the
  rep is private — and couples printed output to an implementation detail the
  declaration is free to change.
- **Instance numbering** (`<counter #3>`): distinguishes instances in debug
  output, but the numbering is allocation-order-dependent, so interpreter and
  backend would need to reproduce identical numbering to keep oracle parity,
  and documented examples would become run-order-sensitive. Not worth it.

**Recommendation: yes — opaque `<counter>`, not serializable.**
