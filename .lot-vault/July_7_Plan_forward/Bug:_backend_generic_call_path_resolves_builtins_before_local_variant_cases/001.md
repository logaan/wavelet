# Bug: backend generic call path resolves builtins before local variant cases

Pre-existing bug found while researching "0.1 Decision: constructing tuple
values in source" (lot:033lMg3lFvO9LLepj3efMs), update 011. Verified on main
2026-07-07.

## Symptom

The wasm backend's *generic* call path resolves builtin names before local
variant case constructors — the opposite precedence from the interpreter and
the checker, both of which resolve user Fn defs → variant cases → builtins.

- Oracle: `DefType` does `env.define(case, CaseCtor)` (src/interp.rs:323),
  shadowing the base-env builtin binding.
- Checker: `check_call` consults `variant_cases` *before*
  `check_builtin_call` (src/check.rs:1948-1952).
- Backend generic path: `call()` checks `BUILTINS` before `local_cases`
  (src/emit/call.rs:297 vs :303). The canonical/mem path resolves correctly.

## Repro

After `DefType t [not(u32) other]`:

- `to-string(not(5))` — interpreter says `"not(5)"`; the compiled component
  returns `"false"` (builtin `not` ran instead of the case constructor).
  **Silent divergence.**

After `DefType mylist [zip(u32) other]`:

- `to-string(zip(30))` — interpreter says `"zip(30)"`; the backend fails the
  build with ``` `zip` expects 2 argument(s), got 1 ```. Loud divergence.

A `Match` over the constructed variant (canonical/mem path) compiles and runs
correctly — only the boxed/generic path diverges.

## Fix

Check `local_cases` before `BUILTINS` in `call()` (src/emit/call.rs), matching
the oracle and checker precedence. Add a differential test covering a variant
case that shadows a builtin name on the boxed path (e.g. `to-string` of the
constructed value).

Relevance raised by tuple constructors: `tuple0`..`tuple16` become builtin
names, so a user variant case named e.g. `tuple2` would shadow correctly in
the oracle and checker but hit this same backend divergence.
