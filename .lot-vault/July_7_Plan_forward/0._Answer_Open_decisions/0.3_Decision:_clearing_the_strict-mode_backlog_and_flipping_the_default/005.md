# Plain-language rewrite: what this decision is actually about

No implementation done — this update just re-explains the situation and answers
"can we just delete these functions?" with evidence from the repo and its history.

## The background you were assumed to know

Wavelet today is **gradually typed**: the compiler has a type checker, but when
it can't work out an expression's type it shrugs ("Unknown") and lets the
program run anyway, with checks happening at runtime. An earlier decision
(already settled) was to end that: make Wavelet **fully statically typed, one
dialect**. The mechanism is a `--strict` flag — under it, "I can't work out this
type" becomes a compile error instead of a shrug. The plan: once every
documented example and the conformance suite compile cleanly under `--strict`,
make strict the permanent default and delete the lenient mode entirely.

The blocker: **17 of the 86 runnable examples in the docs fail under strict**,
all with the same error, "cannot infer a static type". This Thing asks how to
clear those 17. That's all that's going on.

## What the 17 failures actually are

They fall into three plain categories:

1. **Untyped function parameters (~8 examples).** The docs write lambdas like
   `Fn {x} mul(x x)`. The checker currently makes no attempt to work out what
   `x` is, even when it's obvious from context (mapping over a list of
   integers). Writing `Fn {x: s64} mul(x x)` fixes each one today. Nothing here
   is a deletable "function" — it's ordinary code like `map`, `filter`,
   `Def square`, and two `Match` examples. The only question is whether the
   *docs* should carry annotations everywhere, or the *checker* should learn
   the obvious inference so the docs stay clean.

2. **Functions used as values (~5 examples).** Passing a function to a
   function (`twice(inc 10)`), returning one (`adder(5)`), putting them in a
   list, or calling one via `apply`. The checker's support for
   "function-typed values" is rudimentary, so these can't be typed yet.

3. **Specific typing gaps (~4 examples).** Self-recursive functions (the
   checker can't infer a result type through the recursive call, and there's
   no syntax to annotate one); `cell` (the mutable-state primitive has no
   static type); one macro example that expands into an option-typed hole.

## "Can we just delete these functions? Did I even ask for them?"

I checked the history. **None of this is late-stage AI improvisation — every
implicated feature is specified in `design.md` draft 0.1**, the founding design
document that was copied into the repo at Phase 0 (it was removed from the
working tree in "tidied up notes"; read it with `git show c2de455:design.md`):

- **`cell`** — design.md: *"There is no loop construct, no mutation form, and
  no early return… mutable state lives in resources (a `cell` resource ships
  in the standard library)."* Cells are the language's **only** mutable state,
  and the conformance suite's Component Model *resources* are implemented with
  them (`conformance/wavelet/src/roundtrip-resources.wlt` — the counter
  resource is a cell). Deleting cells deletes stateful resources. **Not
  deletable.**
- **Recursion** (`tail-count-down`, `tail-sum-to`) — the design deliberately
  has no loop construct; tail recursion *is* iteration in Wavelet. Deleting
  these examples means "you can't write a loop under strict". **Not
  deletable.**
- **Higher-order functions** (`map-square` is the first example on the docs
  intro page; `twice`, `adder`) — first-class functions are the language's
  identity and teaching style throughout. **Not deletable.**
- **`fold`** — listed by name in design.md's standard-library section
  (`…map filter fold zip…`). Also exercised by the wasm-backend tests. You
  *could* drop it, but it's "sum a list", and the checker work that types
  `map`/`filter` (which certainly stay) types `fold` for nearly free. Deleting
  it dodges almost nothing.
- **`apply`** — design.md §4.1: call syntax requires a *name* in head
  position, so *"to call a computed function value, use apply"*. This is the
  one genuine deletion candidate: `Let {f: get(ops 1)} f(21)` now covers the
  same need (typed Let-bound closures already pass strict). Deleting `apply`
  would clear 2 of the 17 (`std-apply`, `eval-apply-list`) and remove a
  hard-coded "type unknown" in the checker. Cost: a documented design feature
  and a handful of tests go away.
- **`try-let`** — the design doc's flagship macro (§7.2, error propagation
  without early return). The failure is a checker gap in macro expansion, not
  the macro's existence.

**The honest bottom line on deletion:** the 17 are doc examples, but strict is
slated to become the *only* mode — so any feature that can't be typed doesn't
just lose its example, it becomes unwritable in the language. Deleting examples
only "works" where you'd genuinely delete the feature. By that test, deletion
buys you `apply` (2 examples) and arguably `fold` (1), and nothing else. The
other 14 sit on load-bearing features (loops-via-recursion, mutable state,
first-class functions) or are fixed by a one-line type annotation.

One more finding: the flip gate also requires the **conformance suite** to pass
under strict, but nothing currently runs it under strict — and its resource
code leans on `cell-get`, which the checker types as Unknown. So the cell
typing gap blocks the gate through conformance too, independent of the docs.

## The decision, restated simply

Three independent calls, none requiring the old A/B/C/D bucket jargon:

1. **The ~8 easy ones** — annotate the docs examples (quick, docs get more
   verbose) or teach the checker obvious parameter inference (more checker
   work, docs stay clean)?
2. **`apply`** — delete it (and optionally `fold`), or type it? This is the
   only place "just delete it" genuinely applies.
3. **The unavoidable work** — recursion result inference, a static cell type,
   function-value typing, the macro hole. These must be built regardless,
   because the features they type are structural. This is the bulk of the
   effort and no rewrite or deletion avoids it.

A one-line answer like "annotate the docs, delete apply, keep fold, do the
unavoidable work" (or any mix) is enough to unblock this.
