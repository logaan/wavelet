# Restated: the problem and the question

## Problem

Nothing in the project's checks limits function length, file length, or
complexity, and nothing gates on test coverage — `emit.rs` grew to 14k lines
with a 1,750-line method before anyone was forced to notice. You've already
said you want static analysis in the checks; that part is settled. What's
undecided is the enforcement mechanism.

## The question

**How should the size/complexity/coverage limits be enforced?**

- **(a)** In-repo hard gates: clippy's `too_many_lines` and
  `cognitive_complexity` lints at deny, a small file-length script, and a
  cargo-llvm-cov `--fail-under-lines` threshold — all wired into one
  `scripts/check.sh` run locally and in CI. Thresholds start where the
  current tree passes, then ratchet. No new toolchain dependencies.
- **(b)** Dedicated analyzers (lizard / rust-code-analysis / tokei): more
  precise metrics, but new non-Rust tool dependencies for contributors and
  CI, plus duplicate configuration.
- **(c)** CI-only advisory reports that never fail the build: no local
  friction, but nothing actually stops the next monolith.

Recommendation: **(a)**, with initial thresholds ≈150-line functions,
cognitive complexity ≈30, ≈1,500-line files, and coverage at today's
measured value (the implementing session measures first and records the
numbers in the check script).

Answer with one update: "(a)" (optionally with your own thresholds) / "(b)"
/ "(c)".
