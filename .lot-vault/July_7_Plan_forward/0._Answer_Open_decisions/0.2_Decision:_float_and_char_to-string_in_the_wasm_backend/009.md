# WAVE-spec audit of the new output (follow-up on PR #40)

Checked every representation the new code prints against the official WAVE
grammar (`wasm-tools` `crates/wasm-wave/wave_ebnf.md`):

- **Floats: fully valid.** `nan`/`inf`/`-inf` are WAVE's exact spellings;
  `-0.0`, `1e6` (exponent without fraction), `2.5e-7` all parse; our
  exponents never carry leading zeros (WAVE requires that); we never emit
  `1.`/`.5`/`-nan`.
- **Chars: one violation, fixed.** WAVE's escape set is `\' \" \t \n \r \\
  \u{..}` — there is no `\0`, and Wavelet's own reader rejects it too. Rust's
  `{c:?}` spells NUL `'\0'`, so to-string of a NUL char produced unreadable
  text. Oracle and backend now both print `'\u{0}'` (pushed to PR #40,
  ebfc4e9; CHANGELOG updated).
- **Pre-existing deviations, not touched:** unit prints `{}` but WAVE spells
  the empty record `{:}` (`{}` is the empty *flags* value); an empty
  homoiconic tuple prints `()` (WAVE tuples need ≥1 element); NUL inside
  *strings* keeps Rust's `\0` spelling in the oracle.

Filed lot:033wpbyZGIPp8UWFETiUId (top-level) proposing we add the official
`wasm-wave` parser (bytecodealliance/wasm-tools, the implementation wasmtime
uses) to the test pipeline so WAVE compliance is a checked invariant, with
the deviations above allowlisted or fixed.
