# Restated: the problem and the question

## Problem

A documented feature behaves differently on the two execution paths. The
interpreter lets you apply a **record** payload to a multi-parameter closure,
binding fields to parameters by name — the documented `std-apply` example
`apply(Fn {a: s64 b: s64} add(a b) {a: 20 b: 22})` does exactly this. The
compiled path traps on the same program, because the generated closure
wrapper only accepts tuple bundles. The two paths must agree on every
program; this disagreement keeps a differential SKIP entry and its
interpreter fallback alive.

## The question

**Which side changes to close the gap — the backend, the language, or
neither?**

- **(a)** Change the backend: teach the closure wrapper to accept a record
  payload and bind fields by name, matching the interpreter. Small,
  self-contained, backend-only; no docs or semantics changes.
- **(b)** Change the language: make applying a record to a multi-param
  function a static error, and change the interpreter and the documented
  example to match. Shrinks a working, documented feature.
- **(c)** Neither — park; the SKIP entry and fallback stay.

Recommendation: **(a)**, scheduled with the values-callee/backend work.

Answer with one update: "(a)" / "(b)" / "(c)".
