# 0.7 Decision: record payloads applied to multi-parameter closures (closure ABI)

**Gates: one differential SKIP entry (`std-apply`); contributes to
fallback removal.** Verified against main 2026-07-07.

## Context

The interpreter's parameter binding (`src/interp.rs::bind_params`) binds a
RECORD payload to a closure's parameters **by name** (field set must equal
param set); a tuple binds positionally; a sole parameter takes the payload
directly. The documented example `std-apply` does exactly this:
`apply(Fn {a: s64 b: s64} add(a b) {a: 20 b: 22})`.

The backend's `apply` builtin compiles, but its **closure wrapper requires a
TAG_TUP bundle** — an n-param closure invoked with a record payload traps
(`tests/differential.rs`: `const APPLY_REC` / entry `std-apply`). This is a
closure-ABI gap, not a builtin gap.

## Options

- **(a) Extend the closure ABI — RECOMMENDED.** Teach the n-param wrapper to
  accept a record payload and bind fields to params by name, mirroring
  `bind_params` (name-set equality check, then per-field extraction in param
  order). Small and self-contained; done in the wrapper generation so every
  indirect application site benefits, not just `apply`. Backend-only
  (oracle already defines the semantics); differential entry comes off the
  SKIP list as the acceptance test; conformance re-run; no docs/grammar
  changes.
- **(b) Reject record-payload application statically** — make the checker
  error on applying a record to a multi-param function value, and change the
  interpreter to match. Shrinks a working, documented language feature;
  requires a semantics change to the oracle + regen of the rewritten example.
- **(c) Park** — the SKIP entry and its fallback stay.

## Recommendation

**(a)**, scheduled with the values-callee/backend work.

## How to answer

One update: "(a)" / "(b)" / "(c)".
