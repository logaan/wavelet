# Plain-language explanation (verified against main 2026-07-28)

## The background you were assumed to know

Wavelet has two engines — the interpreter (`src/interp.rs`, the reference
semantics) and the compiled wasm path — and a harness
(`tests/differential.rs`) that runs every documented example through both and
compares. Known disagreements sit in a SKIP list; each one keeps the
interpreter-fallback machinery alive. This decision is about one specific
SKIP entry.

The feature: calling a function with a **record** binds fields to parameters
**by name** — `f({a: 20 b: 22})` fills `a` and `b` regardless of order. That
works fine on both engines when the compiler can see which function is being
called. The gap is **indirect** calls — invoking a function *value* (one
passed around as data, e.g. via `apply`). Compiled code routes those through a
generated "wrapper" function, and that wrapper currently only understands
positional argument bundles, not records. So the documented example
`apply(Fn {a: s64 b: s64} add(a b) {a: 20 b: 22})` works in the interpreter
and traps when compiled.

Verified today: SKIP entry `std-apply` (`tests/differential.rs:60`, reason at
line 48: "record payload applied to a multi-param closure (closure-ABI
gap)"). After PR #40 lands it is one of only three SKIPs left.

## The actual question

**The two engines disagree on `apply(two-param-fn, record)`. Which side moves?**

- **(a) Fix the backend** — teach the generated wrapper to accept a record
  and bind fields by name, exactly mirroring the interpreter's `bind_params`.
  Small, self-contained, no language or docs change. The interpreter already
  defines the semantics; this just makes the compiled path honour them.
- **(b) Shrink the language** — make "record applied to a multi-parameter
  function value" a compile-time error, and change the interpreter and the
  documented example to match.
- **(c) Park** — the SKIP entry and the fallback stay.

## Interaction with decision 0.3 (worth deciding together)

In 0.3, `apply` itself is the one genuine deletion candidate. That matters
here: `std-apply` is the only documented program that hits this gap, so
**if you delete `apply` in 0.3, this decision mostly dissolves** — the example
goes away, the SKIP entry goes away, and option (b) becomes nearly free
because the feature loses its only documented use. The underlying question
(can a function *value* receive a record payload?) would still resurface
later inside 0.3's function-value typing work, but nothing would gate on it.
If `apply` stays, (a) is the natural fix and is scheduled with the
values-callee backend work anyway.

## Recommendation

**(a)** if `apply` survives 0.3; if you delete `apply` there, answer **(b)**
here and this Thing closes with it.

Answer with one update: "(a)" / "(b)" / "(c)".
