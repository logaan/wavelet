Researched both questions against main. Answers below; no code touched yet.

## 1. Does WIT allow variadic functions?

**No.** A WIT `func` type is a fixed list of named, typed parameters — the
Component Model has no varargs anywhere. So your principle holds for anything
WIT-facing: Wavelet's user-defined functions (`Def`/`Fn`) have fixed parameter
records, exports must have WIT-expressible signatures, and none of that would
change.

But `tup` would not be a WIT-facing function. Builtins never appear in a
synthesized WIT world — they are compiler intrinsics, and there is already a
genuinely variadic one: **`str-cat`** takes any number of arguments (the
interpreter folds over the whole payload in `src/builtins.rs:541`, the checker
loops over all arg types in `src/check.rs:2324`). Variant constructors
`ok`/`err`/`some` likewise accept whatever bundle they're given.

The deeper point: variadic builtins fall out of the calling convention rather
than being a separate mechanism. §4.2 bundling (`src/interp.rs:143`, mirrored
in `src/emit/call.rs:208`) means *every* call site already packages ≥2
arguments **as a tuple** before the callee sees them. So `tup(a b c)` doesn't
introduce variadics — it just *names the bundle*: in the interpreter it is
almost literally the identity function on its already-bundled payload. That's
also why it can't leak into WIT.

One real wrinkle from that same fact: `tup(x)` bundles to bare `x`, so genuine
1-tuples don't come for free (the builtin can't distinguish "one tuple
argument" from "several arguments"). The conformance callee only needs 2- and
3-tuples (`roundtrip-values.wlt:188-201`), so my lean is: **make `tup` require
≥2 arguments statically** (checker error below 2), matching the bundle
identity exactly, and revisit 0/1-tuples only if a WIT-level need appears. The
alternative — dispatching on syntactic arity at the call site so `tup(x)` is a
real 1-tuple — is implementable but needs arity plumbing the builtin path
doesn't currently have.

## 2. `Tup(a b c)` as a stdlib macro expanding to `Quasi (Unquote a …)`?

The input side works exactly as you pictured: a 1-param macro invoked with
several explicit args receives them as one tuple form
(`src/interp.rs:440-444`). But I'd argue against it, because the macro doesn't
buy the thing that's actually missing:

- **It types as `tree`, not `tuple<…>`.** Macros expand ahead of the checker,
  so by check time `Tup(a b c)` *is* `Quasi (…)`, and `Quasi` types as the
  `tree` interchange type (`src/check.rs:1772`). The conformance exports need
  real `tuple<u8, string, bool>` types in the synthesized WIT. Today only a
  `The tuple(u32 string)` ascription rescues a Quasi — and the macro can't
  emit that ascription because it sees forms, not element types. Users writing
  `The tuple(…) Tup(a b)` everywhere loses the ergonomics that motivated the
  macro. A `tup` builtin instead infers `Type::Tuple(arg_tys)` directly — no
  ascription needed.

- **The backend work isn't saved — it grows.** In the backend, `Quasi` lowers
  to the *boxed* tree representation (a `TAG_TUP` box of boxed elements,
  `src/emit/boxes.rs`), not the canonical-ABI tuple that boundary lowering
  and `mem_field_ok` need. The missing piece for the values callee is exactly
  the canonical constructor + the `WitTy::Tuple` arm — option (a)'s work — and
  the macro route still needs all of it, except now the backend must recognize
  a macro-expansion *pattern* (`The tuple(…) Quasi (Unquote …)`) instead of a
  simple builtin head. More work, more fragile.

- **Stdlib practicality.** The bundled stdlib macros (`If`/`Do`,
  `STDLIB_MACROS` in `src/builtins.rs`) work because they expand to `Match`, a
  core construct every stage already handles; `Tup` would expand to something
  the stages handle only as tree data. The macro body itself is also awkward:
  building a variable-arity Quasi template means nested quasi + `Splice` +
  wrapping each element form in an `Unquote` call, and the received
  tuple-of-forms isn't directly `map`-able (map wants a list). And a macro
  isn't first-class — builtin `tup` is a value you can pass around
  (`Value::Builtin`), `Tup` wouldn't be.

So `Tup`-as-macro is essentially option (d) with nicer spelling, and it still
requires option (a)'s checker + backend machinery underneath. Given that, the
lowercase builtin also fits the naming split better: TitleCase heads are
macro/arity-read territory in the reader; `tup` sits naturally beside `zip`
and `str-cat`.

## Where that leaves the decision

Still recommending **(a)**, now with the arity shape pinned down: `tup` is
variadic at ≥2 arguments (a static checker error below that), defined as
exposing the §4.2 argument bundle. Happy to go with syntactic-arity 1-tuples
instead if you want them from day one — say so in your answer and I'll fold it
in. Otherwise reply "(a)" and I'll execute the sketch as written.
