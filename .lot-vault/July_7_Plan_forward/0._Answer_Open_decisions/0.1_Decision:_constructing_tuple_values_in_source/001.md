# 0.1 Decision: constructing tuple values in source

**Gates: the conformance values callee (the last blocker), and closes a real
hole in "the full WIT surface is expressible".** Facts below were verified
against main on 2026-07-07.

## Context

Wavelet has **no way to construct a `tuple` VALUE from computed data**. Tuple
*patterns* destructure fine (interp + backend), tuples cross component
boundaries fine (lift/lower work), but nothing evaluates to a fresh tuple
except the `zip` builtin (pairs only, inside a list) and `Quote`/`Quasi`.

- Parens are ONE node (`Node::Tup`, `src/form.rs`): a **call** in eval
  position, a tuple only under Quote. `(1 "a")` errors ("call head must be a
  name"); commas lex as whitespace so `(1, "a")` is the same call form. This
  is settled design — do not reopen.
- The printer emits tuples as `(1, "a")` (canonical WAVE text), which the
  reader cannot evaluate back — a known reader/printer asymmetry.
- `tup` is bound nowhere: absent from `src/builtins.rs::NAMES` and from the
  backend builtin dispatch. (`"tup"` strings in the tree are the `form-kind`
  reflection tag, not a constructor.)
- The checker already blesses `The tuple(u32 string) Quote (1 "a")` (literal
  only) and `The tuple(u32 string) Quasi (Unquote add(1 2) "x")` (computed,
  but meta-flavoured); neither lowers to a canonical tuple in the backend.
- The backend can *represent* tuples (boundary lift/lower, patterns,
  `node_mem_ty` admits the layout) but has **no constructor**, and
  `mem_field_ok` has no `WitTy::Tuple` arm, so a tuple can't be a canonical
  variant/result/record payload built in source.
- The conformance values callee
  (`conformance/wavelet/src/roundtrip-values.wlt`) needs to REBUILD tuples
  from computed elements (`tup(wrap-u8(n) bump-str(s) not(b))` etc.) in
  `tuple-rt`, `tuple-nested-rt`, `result-tuple-direction-rt`. A WIT export
  set is all-or-nothing, so these three keep the entire values callee
  un-buildable. It is otherwise DONE (all 35 exports type-check and
  WIT-synthesize).
- Docs currently overclaim: `docs/docs/language/values.mdx` lists
  `("abc", 123)` as tuple value syntax; `roadmap.mdx` marks backend tuples
  done. Whatever is chosen includes a docs correction.

## Options

### (a) A `tup` variadic builtin — RECOMMENDED

`tup(a b c)` evaluates its arguments and returns a tuple of exactly that
arity; result type = tuple of the argument types (no ascription needed;
`The tuple(…)` still unifies element-wise). Tuples are positional, so
construction order = ABI order — no normalization hazard.

- Oracle: add `"tup"` to `src/builtins.rs::NAMES`; return `Value::Tup` of the
  evaluated args at exact arity. Decide the 0/1-arg shape deliberately —
  `tup(x)` a genuine 1-tuple, `tup()` the empty tuple — independent of the
  ≥2-only argument-bundling collapse in the calling convention.
- Checker: `"tup" => Ok(Type::Tuple(arg_tys))` in `check_builtin_call`.
- Backend: add `tup` to the builtin dispatch (`src/emit/builtins.rs`); lower
  to an in-place canonical tuple reusing the canonical-record constructor
  path (tuple = positional record); add a `WitTy::Tuple` arm to
  `mem_field_ok` so tuples work as variant/result/record payloads.
- Pros: the callee compiles as-written; symmetric with working tuple
  patterns; no reader/lexer/grammar change; doesn't touch the settled paren
  semantics. Cons: most backend work of the options; one new builtin name to
  mirror into the three grammars' builtin lists + LSP + stdlib docs.

### (b) A dedicated literal syntax

`(1, "a")` is a non-starter (commas are whitespace; parens are calls; reopens
the settled paren decision). A new bracket (`#(…)` etc.) avoids that but is a
lexer+reader+all-three-grammars+regen change and still needs (a)'s evaluation
semantics — (a) with extra syntax.

### (c) No new surface — tuples stay boundary-only

The three callee functions have no faithful rewrite (each must *return* a
tuple built from computed values), so this means dropping/degenerating those
exports and the matching WIT world entries, weakening tuple ABI coverage, and
walking back the docs overclaims. Zero language work.

### (d) Reuse Quote/Quasi as the blessed spelling

`The tuple(…) Quasi (Unquote e …)` works in the oracle today but reads as
macro machinery, wraps every element in `Unquote`, and STILL needs (a)'s
backend construction work to lower. Honest description of today's partial
state, not a good end state.

## Recommendation

**(a)** — it's what the callee already writes, mirrors the working pattern
side, and closes the WIT-surface hole with one obvious constructor.

## Execution sketch for (a)

Oracle first, then checker, then backend (constructor + `mem_field_ok`), with
interpreter unit tests incl. nested `tup(tup(1 2) 3)`; a differential example
(flat, nested, as a result payload); then the values callee builds as-written
— add `conformance/wavelet/test-values-callee.sh` (mirror
`test-resources-callee.sh`), run vs both rust seeds, update that file's
STATUS header + `conformance/wavelet/README.md`. Downstream: `tup` into the
three grammars' builtin lists (the neovim one is the separate `wavelet.nvim`
submodule repo — commit+push there, bump the pointer), LSP builtin set,
`docs/docs/stdlib.mdx`, fix `values.mdx`/`evaluation.mdx`/`syntax.mdx`/
`roadmap.mdx` prose, CHANGELOG `Added`, `./scripts/regen-examples.sh` if a
documented example is added.
