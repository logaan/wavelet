Good challenge — the answer hinges on what "macro expanded into a straight
tuple" would even mean, so let me be precise about what each stage does.

## Expansion rewrites forms to forms, and there is no tuple form to rewrite into

Macro expansion replaces `Tup(a b c)` with the form
`Quasi (Unquote a Unquote b Unquote c)` — and then it **stops**. `Quasi` is not
itself a macro that expands further; it is a terminal core form, and the
expander deliberately does not descend into it (`src/expand.rs:289` copies
Quote/Quasi bodies verbatim, because their contents are data). So the fixpoint
of expansion still *contains* the `Quasi` node.

For expansion to go one step further and produce "a straight tuple", there
would have to exist a source form that IS a tuple in evaluation position — and
that form is exactly what the language lacks (it's the hole this whole decision
is about). Parens in eval position are a call, per the settled design. `Quasi`
doesn't expand into a tuple; `Quasi` is the closest thing to a tuple expression
the form language has.

## At runtime you're right — the interpreter does produce a real tuple

Evaluating that `Quasi` runs the `Unquote` holes and builds `Value::Tup` of the
results (`src/interp.rs:485`). Dynamically there is no "tree wrapper" — trees
and tuples share the same runtime representation in the oracle. That's exactly
why option (d) works in the interpreter today.

## The gap is static: the checker cannot tell "tuple of values" from "code"

The checker runs on post-expansion forms, so it sees `Quasi (…)`, and it types
every `Quasi` as `tree` (`src/check.rs:1776`). It checks the unquote holes'
expressions, but their types don't flow anywhere.

Could it be smarter — "a splice-free Quasi whose elements are all Unquotes
types as `tuple<…>`"? Here's the fundamental problem: in Wavelet a **call form
is a tuple node**. `Quasi (Unquote f Unquote x)` is, byte for byte, both

- "the 2-tuple of the values of `f` and `x`", and
- "the call form `f(x)` with both subforms computed" — the bread-and-butter of
  a macro template building code.

Same shape, two meanings, and only the programmer knows which one they meant.
Typing that Quasi as `tuple<…>` would silently break every macro template that
computes a call head or builds a fixed-arity call — the checker would claim
it's a tuple when the macro means it as code to hand back to the expander.
`tree` is the only sound answer for Quasi in general; the `The tuple(…)`
ascription is the current escape hatch precisely because it's the programmer
stating which reading they meant.

`tup(a b c)` resolves the ambiguity at the head symbol instead: it can only
mean "tuple of these values", so the checker infers `Type::Tuple(arg_tys)`
directly, no ascription.

## And the backend gap is representational, independent of typing

Even if the checker were taught the special case, `Quasi` lowers in the wasm
backend to the *boxed tree* encoding (a `TAG_TUP` box of boxed elements), not
the flat canonical-ABI tuple that boundary lowering, `mem_field_ok`, and the
conformance exports need. Bridging that means adding the canonical tuple
constructor — option (a)'s work — plus backend pattern-recognition of the
expanded `The tuple(…) Quasi (Unquote …)` shape as the trigger. So the macro
route pays (a)'s cost and adds fragility on top; it saves nothing.

## Bottom line

Your runtime intuition is correct — the Quasi *evaluates* to a straight tuple
in the oracle. But it never *expands* to one (no such form exists), the checker
can't soundly type it as one (tuple-of-values and call-form-as-code are the
same tree), and the backend doesn't represent it as one (boxed tree vs
canonical ABI). A `tup` builtin fixes all three at once by making the intent
unambiguous at the head. Still recommending **(a)**.
