Researched the collision question against main (all claims below verified by
building/running real programs today). Short answer: **the collision you're
worried about is already resolved by the language, in the direction you want —
variant cases shadow builtins.** And separately: 0/1-arity `tup` is
implementable, but the hard part is §4.2 bundling, not naming. Details:

## 1. A variant case named `tup(a)` stays expressible — cases shadow builtins

This exact collision already exists for every current builtin (`zip`, `not`,
`some`, `ok`, `map`, …), and the language has a settled answer. I tested it
with `zip`:

```
DefType mylist [zip(u32) other]

Def run Fn {}
  Match zip(30) [((zip n) str-cat("zip case: " to-string(n))) (other "other")]
```

- **Interpreter (the oracle)**: `DefType` does `env.define(case, CaseCtor)`
  (src/interp.rs:323), shadowing the base-env builtin binding. `zip(30)`
  constructs the variant; verified in the repl (`zip(30)`, `not(5)` both come
  back as variant values).
- **Checker**: `check_call` consults `variant_cases` *before*
  `check_builtin_call` (src/check.rs:1948-1952), so the case ctor wins
  statically too. Precedence is user `Fn` defs → variant cases → builtins.
- Cross-package cases don't collide at all — dep-declared cases are reached
  qualified (`alias/case`).

So if `tup` becomes a builtin, a module that declares a variant with a `tup`
case keeps constructing it as `tup(a)`; that module just loses the tuple
builtin locally — the identical trade-off you accept today by naming a case
`zip` or `some`. No new expressiveness hole.

**Caveat — I found a pre-existing backend bug while verifying this.** The wasm
backend's *generic* call path checks `BUILTINS` before `local_cases`
(src/emit/call.rs:297 vs :303) — the opposite precedence from the oracle and
checker. The canonical/mem path resolves correctly (my `Match` example above
compiles and returns `"zip case: 30"` under wasmtime), but force the boxed
path and it diverges:

- `to-string(zip(30))` after the DefType: interpreter says `"zip(30)"`, the
  backend **fails the build** with ``` `zip` expects 2 argument(s), got 1 ```
  (loud divergence).
- `to-string(not(5))` after `DefType t [not(u32) other]`: interpreter says
  `"not(5)"`, the compiled component returns `"false"` — builtin `not` ran
  instead of the case ctor. **Silent divergence, today, on main,** unrelated
  to `tup`. Fix is to check `local_cases` before `BUILTINS` in `call()`.

(Second incidental find: a multi-payload case like `zip(list(u32) list(u32))`
synthesizes invalid WIT — `zip(list<u32>, list<u32>)`, but WIT variant cases
take exactly one type. Also pre-existing and separate.)

## 2. The real cost of `tup(a)`/`tup()` is §4.2 bundling, not naming

Your want is legitimate at the WIT level: `tuple<u32>` **and** `tuple<>` are
both valid WIT (verified with wasm-tools 44), and Wavelet's type parser
already accepts `tuple(u32)`/`tuple()` (src/check.rs:156 takes any arity). The
empty tuple value even already exists internally — the unit value IS
`Tup([])`, and `tup()` would simply name it.

The obstacle: an ordinary builtin receives only the *bundled* payload
(0 args ⇒ empty tuple, 1 ⇒ the bare value, ≥2 ⇒ tuple), so at runtime
`tup(pair)` and `tup(x y)` are indistinguishable. Supporting 1-tuples means
dispatching on **syntactic** argument count at the direct-call site. The good
news is every stage except the interpreter's builtin dispatch already has the
syntactic args in hand:

- **Checker**: `check_builtin_call` sees the args — `"tup"` ⇒
  `Type::Tuple(arg_tys)` covers 0/1/≥2 uniformly. Shadowing preserved for
  free (variant_cases is consulted first).
- **Backend**: `builtin(fx, name, args)` receives syntactic args — same
  uniform treatment (lowering to the canonical constructor + the
  `WitTy::Tuple` `mem_field_ok` arm, as sketched before).
- **Interpreter**: the one carve-out. It must NOT be a `special_form` — those
  are dispatched by name *before* env lookup (src/interp.rs:126), which would
  preempt a shadowing `CaseCtor` and create exactly the problem you're
  worried about. Instead: in `eval_call`, after `env.lookup` resolves the
  head, if the value is `Value::Builtin("tup")`, build the tuple from the
  syntactic arg list (0 ⇒ `Tup([])`, 1 ⇒ `Tup([v])`, ≥2 ⇒ the bundle as-is).
  Resolution-then-dispatch keeps shadowing intact by construction.

## 3. The one residual wart: first-class `tup`

A `tup` *value* passed to `apply`/`map` only ever sees the bundle, so
`apply(tup x)` can't mean the 1-tuple `(x,)` — the `f(x) ≡ apply(f x)`
equivalence necessarily breaks at arities 0/1 for this one name. Two options:

- (i) bind `tup` as a first-class builtin with bundle-identity semantics
  (agrees with the direct call at ≥2) and document the 0/1 direct-call sugar;
- (ii) make bare `tup` in value position a static error ("call it directly"),
  relaxable later without breaking anything.

I lean **(ii)** — there's precedent (payloaded case ctors as values are
already "call it directly" in the backend, src/emit.rs:710), and it keeps the
oracle and backend trivially aligned.

## Where that leaves the decision

Option (a), amended: `tup` accepts **0, 1, or ≥2 args** (`tup()` = empty
tuple, `tup(a)` = genuine 1-tuple), implemented as syntactic-arity dispatch
*after* name resolution so `DefType` cases shadow it exactly like `zip` today;
bare `tup` in value position is a static error for now. The execution sketch
additionally picks up the backend precedence fix (local_cases before BUILTINS)
— arguably worth landing as its own bug-fix commit since it's a live silent
divergence on main. If that all sounds right, reply "(a)" and I'll execute.
