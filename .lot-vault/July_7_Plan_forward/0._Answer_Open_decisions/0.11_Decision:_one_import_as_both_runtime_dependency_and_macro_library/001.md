# 0.11 Decision: one import as both runtime dependency and macro library

## Context

A package that ships both runtime functions AND macros must currently be
imported **twice** — once as an ordinary dependency, once as a macro library
— because the import surface distinguishes the two roles. This two-import
path is supported and documented (`docs/docs/macros.mdx`). Collapsing it
into a single import that serves both roles needs a new import surface (a
language change: one form whose resolution feeds both the expander and the
component linker), which was deliberately not designed as part of the CLI
chores.

Related but separate (recorded for context, no decision needed): registry
FETCH of macro components (`wavelet add`) is blocked upstream — `wkg`
currently fetches WIT packages only, not components.

## Options

- **(a) Park — RECOMMENDED.** The two-import path works and is documented.
  Design the unified import when a real library ships both roles and the
  ergonomics bite (that library will also expose which resolution corner
  cases matter — e.g. whether the macro half may call the runtime half at
  expand time).
- **(b) Design now**: a single `Import {pkg: … as: … roles: {runtime macro}}`
  (or inferred roles from package contents). Touches the reader/expander,
  dependency resolution, and docs; low urgency, nonzero design risk while
  no consumer exists.

## How to answer

One update: "(a)" / "(b)".
