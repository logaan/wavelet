# Restated: the problem and the question

## Problem

A package that ships both runtime functions **and** macros must be imported
twice — once as an ordinary dependency, once as a macro library — because
the import surface keeps the two roles separate. The double import works and
is documented, but it's an ergonomic wart. Collapsing it into one import
means designing a new import surface whose resolution feeds both the
expander and the component linker — and no published library yet ships both
roles, so there's no consumer to validate the design against.

## The question

**Design the unified single-import form now, or wait for a real dual-role
library to exist first?**

- **(a)** Park: keep the documented two-import path until a real library
  ships both roles — that library will expose which resolution corner cases
  matter (e.g. may the macro half call the runtime half at expand time?).
- **(b)** Design now: a single import form with explicit or inferred roles.
  Touches the reader/expander, dependency resolution, and docs; nonzero
  design risk while no consumer exists.

Recommendation: **(a)**.

Answer with one update: "(a)" / "(b)".
