# Plain-language explanation (verified against main 2026-07-28)

## The background you were assumed to know

Wavelet has two engines. The interpreter (`src/interp.rs`) is the reference
semantics; `wavelet build` compiles programs to wasm components. `wavelet run`
and the REPL prefer the compiled path but **silently fall back to the
interpreter** when the compiled path can't handle a program. A test harness
(`tests/differential.rs`) runs every documented example through both engines
and compares results; the known gaps live in a SKIP list there. The standing
goal is to close every gap and then delete the fallback machinery entirely, so
the compiled path is the only path.

`read` is the builtin that parses a string of Wavelet source text into a form
value **at runtime** — `read("add(1 2)")` gives you the syntax tree of
`add(1 2)` as data. It's the runtime half of homoiconicity, and it's in the
founding design (design.md: *"`to-string(form)` prints canonical WAVE text;
`read(string)` parses it; the round trip is lossless"*). The interpreter
implements it by calling the compiler's own Rust parser. A compiled component
can't do that — there is no parser inside the emitted wasm — so any program
calling `read` traps on the compiled path and falls back. While that hole
exists, the fallback can't be removed.

Verified today: the SKIP entry is `std-read` (`tests/differential.rs:65`,
reason at line 42). Once PR #40 (float/char to-string, decision 0.2) lands,
the SKIP list is down to three entries — `macro-expand`, `std-apply`
(decision 0.7), and this one. Exactly one documented example uses `read`.

## The actual question

**When a compiled component calls `read`, what should happen?**

- **(a) It works, self-contained** — compile a full WAVE lexer+parser into the
  guest wasm. Honest full fidelity, but the largest single piece of backend
  work left, and it must match `src/reader.rs` behaviour exactly, forever.
- **(b) It works, via the host** — the runtime satisfies a `read` import by
  calling the native parser. Cheap, but components using `read` stop being
  runnable on generic WASI runtimes. Quietly forks what `wavelet build`
  produces.
- **(c) It's a compile-time error** — `read` stays available in the
  interpreter/playground/macro world, and the checker rejects it in compiled
  components with a clear message. The one `std-read` example gets rewritten
  or moved. This mirrors how `expand` is already treated on the build path.
- **(d) Do nothing** — the fallback machinery lives forever for this one case.

## On the "can we just delete it?" test (per 0.3)

`read` is design-mandated, not incidental — but only one documented example
uses it, and its interpreter implementation costs nothing to keep. Deleting it
from the language entirely would remove runtime parsing outright; option (c)
is the softer version of that instinct: keep it where it's free, refuse it
where it's expensive. Nothing else in the codebase depends on runtime `read`.

## Recommendation

**(c)** — unless "shipped components can parse Wavelet at runtime" is a promise
you actually want the language to make, in which case (a). Avoid (b); (d)
defeats the whole fallback-removal goal.

Answer with one update: "(a)" / "(b)" / "(c)" / "(d)".
