# Restated: the problem and the question

## Problem

Wavelet's compiled (wasm) path is supposed to run every program the
interpreter runs. The `read` builtin — parse WAVE text into a form value at
runtime — breaks that today: it works in the interpreter, but compiled
components contain no reader, so any program calling `read` traps on the
compiled path and silently falls back to the interpreter. The interpreter
fallback machinery cannot be removed while this hole exists.

## The question

**Should `read` work in compiled components at all — and if so, who
implements it?** When a compiled component calls `read`, what should happen?

- **(a)** It works, via a reader compiled into the guest wasm. Full fidelity
  with the interpreter, but the largest single piece of remaining backend
  work.
- **(b)** It works, via the host satisfying a `read` import. Cheap and exact,
  but components that use `read` stop being self-contained — a generic WASI
  runtime won't run them.
- **(c)** It's a check-time error: `read` becomes an interpreter/playground
  facility only. Honest and low-cost; shrinks the language on the compiled
  path.
- **(d)** Nothing changes: the interpreter fallback stays indefinitely for
  `read` programs.

Recommendation: **(c)** — or **(a)** if runtime `read` in shipped components
is something the language should actually promise. Avoid (b); (d) defeats
fallback removal.

Answer with one update: "(a)" / "(b)" / "(c)" / "(d)".
