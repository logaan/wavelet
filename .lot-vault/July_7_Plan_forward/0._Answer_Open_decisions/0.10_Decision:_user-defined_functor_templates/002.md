# Restated: the problem and the question

## Problem

Generic containers exist in Wavelet only as the single compiler-known `Set`
functor — user code cannot declare its own "component with type parameters".
That's a real expressiveness gap, but nothing currently planned needs a
second generic container, so building the general feature now would be
significant design work (type-parameter scoping, parameterized WIT
synthesis, per-instance emission) with no driving use case.

## The question

**Do we invest in generic-container machinery now — and at what level?**

- **(a)** Park: keep the built-in `Set` until a second container (map,
  queue, …) is concretely wanted, and let that use case drive the design.
- **(b)** Cheap intermediate, when needed: add further compiler-known
  templates on the existing SET_OPS pattern — no new language design, but
  every new container is a compiler change.
- **(c)** Design user-defined templates now: a `DefFunctor`-style
  declaration instantiated by the existing `Instantiate` form. Premature
  without a driving container.

Recommendation: **(a)**.

Answer with one update: "(a)" / "(b) when needed" / "(c)".
