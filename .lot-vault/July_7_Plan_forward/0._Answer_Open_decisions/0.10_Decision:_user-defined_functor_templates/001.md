# 0.10 Decision: user-defined functor templates (generic containers)

## Context

Generic containers work today through ONE compiler-known functor: the `Set`
template. `Instantiate {pkg: "wavelet:coll/set" with: {elem: T} as: alias}`
is the dedicated instantiation form (by-name arguments, ready for
multi-parameter functors), and the `SET_OPS` descriptor
(`src/builtins.rs:81`, mirrored through `src/wit.rs` and the backend
resource machinery) single-sources its inference, emitted WIT, and runtime.
A returned-handle bug through local-record elements was fixed; the mechanism
is sound.

What does NOT exist: **user code cannot define a new functor template** —
"a component with type parameters" declared in wavelet source (a
parameterized interface + implementation). The compiler knows
`wavelet:coll/set` intrinsically. Designing the general feature overlaps the
resource-declaration surface (a functor's exported ops are usually resource
methods — `DefResource` now exists, so the prerequisite is in place) and the
type-parameter story.

## Options

- **(a) Park — RECOMMENDED.** The single built-in Set covers the current
  need; nothing planned depends on user templates. Revisit when a second
  generic container (map, queue, …) is actually wanted — that concrete use
  case should drive the design.
- **(b) Cheap intermediate**: add more compiler-known templates (map, etc.)
  on the same SET_OPS pattern when needed — no new language design, linear
  compiler cost per container, but every container is a compiler change.
- **(c) Design user-defined templates now**: a `DefFunctor`-like declaration
  (type params + a DefResource-shaped body), instantiated by the existing
  `Instantiate` form. Significant design work (type-parameter
  scoping/checking, WIT synthesis of parameterized interfaces, per-instance
  emission); premature without a driving container.

## How to answer

One update: "(a)" / "(b) when needed" / "(c)".
