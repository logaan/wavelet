## Problem

The interpreter's `neg`/`abs` (`src/builtins.rs:400-404`) use raw `-n` /
`n.abs()`, while `add`/`sub`/`mul`/`div`/`rem` all use `checked_*` variants
with a catchable "integer overflow" error. On `n == i64::MIN` the interpreter
panics in debug builds / wraps in release, and the wasm backend wraps — so
unary and binary overflow behave differently, and interpreter and backend can
disagree.

## The question

Do you accept this as work to schedule: `checked_neg`/`checked_abs` raising
the same "integer overflow" error, with the backend made to agree (trap), or
alternatively wrap-for-unary explicitly documented?

## Recommendation

Accept — the smallest finding of the set (on the order of minutes). Fold it
into any nearby scheduled work rather than giving it its own step.
