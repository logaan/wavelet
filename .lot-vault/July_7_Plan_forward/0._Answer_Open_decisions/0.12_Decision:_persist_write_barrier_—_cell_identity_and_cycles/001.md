# 0.12 Decision: persist write barrier — cell identity and cycles

*Broken out of "0.8 Decision: code-review findings triage"
(lot:033lMgJ9BtS8IZM2KpoBXi), finding F2, at your request. Re-verified on main
2026-07-28.*

## Problem

When a resource's state is saved out of the per-call arena into the persistent
region, the write barrier (`persist`, `src/emit/helpers.rs:1866`) deep-copies
the state graph with no tracking of already-copied objects:

1. It copies each `TAG_CELL` fresh — a graph that reaches the same cell by two
   paths becomes two independent cells, diverging from the interpreter's
   `Rc<RefCell>` sharing semantics. Mutations through one path silently stop
   being visible through the other.
2. It self-recurses with no visited set — a cyclic graph traps on stack
   exhaustion.

Reachability today is narrow (the functor `set` persists one flat cell), so
nothing user-visible breaks yet — but this barrier is the contract every
future DefResource `New` state graph relies on. It is a latent correctness bug
that becomes real the moment richer resource state lands.

## The question

Do you accept this as work to schedule — and at which depth?

- **(a) Short-term guard**: document the contract (acyclic, no shared cells)
  and reject violating graphs at compile time.
- **(b) Full fix**: thread an arena-ptr → persistent-ptr identity map through
  `persist`, preserving sharing and breaking cycles.
- **(c) Reject**: leave as-is.

## Recommendation

Accept: (a) now — cheap, and it makes the limitation explicit instead of
silent; (b) when richer resource state is actually scheduled. The original
triage placed F2 in the first tier (alongside F3).
