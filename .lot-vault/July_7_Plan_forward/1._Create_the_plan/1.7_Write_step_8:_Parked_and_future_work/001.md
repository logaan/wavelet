### Future directions (unscheduled ideas)
- **Closures over the wire**: serialise closures as small standalone
  components (exporting `call` over an embedded typed-captures payload) that
  non-wavelet components can invoke, Erlang-style. Viable ONLY via the
  defunctionalization representation (captures are concretely-typed data);
  the resource-lifting route cannot serve it (handles are per-instance
  identity). Pick up after the multi-case dispatch work in step 3.
- Additional deployment targets: standalone CLI (bundled runtime), JS in
  browser/node/bun, JVM, Docker/K8s; publish a wasm build of the compiler.
- The compiler as an importable component (enables closure compilation and
  in-language build pipelines).
- Wavelet as a markup language (a Markdown-class markup as a pure library;
  a detailed design exists in dev-notes/wavelet-as-markup.typ).

### Parked design questions
- Alternatives to the bundled stdlib: push `std: false` toward the stdlib
  being just another pullable dependency; purely-functional or real-time
  variants.
- Unify qualified references with record access and call-chaining: could
  `foo/bar` become `foo.bar()` if qualified imports returned a record with
  virtual accessors; `1.increment()` → `(increment 1)` as pure rewriting.
- Boundary name-mangling control: when an overload set is exported, are WIT
  names compiler-chosen or user-controlled via `Export`?
- Overload declaration syntax: implicit same-name sets vs an explicit
  grouping form; the exact resolution algorithm and its interaction with
  `The`.
- Recursion: resources vs arenas — should a derive generate an arena
  representation (+accessors) for a recursive type instead of hand-rolled
  arenas?
- The Derive surface and extent: is `Derive {Eq Ord Show} t` right; which
  classes ship built-in; user-authored derivers? (Note: Derive on resource
  types is an ERROR by settled design — resources are identity-equal.)
