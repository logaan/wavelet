## 7.4 assessment (goal-7 session 1)

Confirmed the current model: `macros: true` is compile-time-only by design
(macros.mdx:89; wit::is_macro_only returns true whenever imp.macros). A single
import projecting BOTH a runtime import (in the synthesized world + composition)
AND a compile-time macro instance would require a new import surface — one
import form yielding two surfaces. That is a language-surface/semantics addition,
which is explicitly OUT OF SCOPE for the goal-7 execution session (semantics
changes deferred). So NOT implemented this session.

Pragmatic resolution landed instead (in scope, no semantics change): a package
that provides both is imported TWICE — once `macros: true` (compile-time) and
once as an ordinary runtime import. Verified structurally sound: the two forms
are independent; build.rs skips the macro-only one (is_macro_only) and creates a
Dep only for the runtime one; the macro resolver caches by package and doesn't
interfere with world synthesis. Documented in docs/docs/language/macros.mdx and
refined the code comments in wit.rs (is_macro_only) and build.rs to reference
this Thing and the two-import path.

Design sketch if/when the single-import form is wanted (a future language slot):
add an explicit opt-in field to the import record (e.g. `macros: true runtime:
true`), then split is_macro_only into is_macro/is_runtime and thread the
runtime-surface flag through the three import parsers (wit::collect,
macrodep::parse_macro_import, runner::parse_import), world synthesis, build dep
resolution, and the interpreter runner, plus docs + grammars (no new token —
`runtime` is just a record key) + tests. Non-trivial; belongs behind a decision
or a dedicated language-feature slot, not a build/CLI chore.
