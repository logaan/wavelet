# Decision: clearing the strict-mode backlog (so `--strict` can become the default)

This is the endpoint of goal 3 (3.9 "Add strict mode, then make it the
default"): the accepted plan shipped `--strict` opt-in and said flip it to the
DEFAULT once the documented-example + conformance suites pass under it, then
delete gradual mode. The backlog blocking the flip is 17 of 86 documented
examples. Goal-5 session 14 landed arrow types and proved them **necessary but
not sufficient**. This Thing gives you the verified per-example breakdown, the
options for clearing it, and a per-option plan — answer with one line.

Everything below the code fences was verified against the current tree
(`target/debug/wavelet --strict run <file>`) on 2026-07-07; the exact reasons
each rewrite passes or fails are from that binary, not from memory.

---

## 1. Context (verified against the current tree)

### How strict mode works today

`--strict` is parsed in `src/main.rs` (lines 9-11): it strips the flag and calls
`wavelet::check::set_strict(true)`. In `src/check.rs` (~line 540) `STRICT` is a
process-wide `AtomicBool`; when set, any expression the checker can only type as
`Type::Unknown` is a compile error — "`cannot infer a static type for this
expression (strict mode)`". Declaration heads and unexpanded macro calls are
exempt; macro *output* is checked strictly post-expansion. It is opt-in on every
subcommand (`wavelet --strict run|build|wit …`).

### The accepted flip plan (3.9 / 3.10 — summarized faithfully)

- **3.9** (`lot:033iWQAotHn8zcEvt2Sjko`, answered by Logan 2026-07-02):
  **option-1 objective green gate** — flip the default when the documented
  example suite (`docs/examples.json` → `tests/examples.rs`) **and** the
  conformance suite both pass under strict. Two accepted riders: (a) from now on
  all new examples/conformance programs are authored strict-clean, so the
  backlog only shrinks; (b) once flipped, **delete gradual mode** rather than
  leaving it as a non-default flag (a lingering gradual dialect "quietly undoes
  2.2.6"). Until then, "the failure list under strict IS the burn-down backlog"
  (the ignored `strict_backlog` diagnostic in `tests/strict_mode.rs`).
- **3.10** (`lot:033iWUy0fzRoneJ9hZWPAC`): the example-suite sweep. The
  non-function-value rewrites already landed on `goal-3-total-types`
  (sf-if-nonbool → compile-time "If condition must be a bool", pm-no-clause →
  non-exhaustive diagnostic, heterogeneous-list examples rewritten to records,
  etc.), re-locked via `./scripts/regen-examples.sh`. 3.10 explicitly parks its
  **remaining** sweep work "at the strict flip (blocked on function types)".

So the flip itself, once the backlog is 0, is small and prescribed: make strict
the default (default `STRICT` true / drop the flag branch and the gradual code
path so `Unknown` is *always* an error), finish the 3.10 sweep of any last
examples, then delete gradual mode. It is gated only by the 17 examples.

### What session 14 established (goal 5, 5.8 defunctionalization)

`lot:033iYvSRtJneYx1zERPfFM` update 004 + the session-14 checkpoint
(`lot:033kvZMvv5HhRdg0nah7gu`): the checker grew **Phase D arrow types**
(`Type::Fn`). A `Fn` literal with fully-concrete params+result carries
`(P…) -> R`; a bare single-signature concrete-arrow `Def` reference is a
zero-capture value of that arrow; indirect application of a function-typed
**local** is checked (`check_indirect_apply`). The boundary rule (function types
can't cross component boundaries) and zero-capture backend devirtualization also
landed. **Still remaining in 5.8:** `Fn`-literal (capturing) devirtualization
and the multi-case variant+dispatch generation.

The checkpoint's finding, which this Thing resolves: **arrow types are necessary
but not sufficient.** The 17 backlog examples are authored with *untyped* params,
so no concrete arrow ever forms, and several need work beyond param typing.

### The 17, bucketed by what actually clears each one (verified)

Run `cargo test --test strict_mode strict_backlog -- --ignored --nocapture` to
reprint the raw list (all 17 fail identically with "cannot infer a static
type"). What differs is the *fix* each needs. I rewrote representatives and ran
them under `--strict`; results:

**Bucket A — clears with typed params alone; checker UNCHANGED (6).** Adding a
param/ascription type makes these pass strict as-is:

- `map-square`, `std-map`, `std-filter` — type the lambda param, e.g.
  `map(Fn {x: s64} mul(x x) [1 2 3 4 5])` → passes. (`map` returns
  `list<unknown>` and `filter` returns its list arg; the `List` wrapper is
  "concrete enough" not to trip strict, so only the untyped lambda param was the
  error.)
- `eval-fn-scalar` — `Def square Fn {n: s64} mul(n n)` → passes.
- `pm-describe` — `Def describe Fn {r: result(s64 string)} …` → passes.
- `pm-none` — ascribe the scrutinee: `Match The option(s64) none [ … ]` →
  passes.

**Bucket B — needs a typed higher-order builtin signature; rewrite alone
CANNOT fix (2).** The builtin's own result type is hard-coded `Type::Unknown` in
`check.rs` (lines 2404-2406: `"map" => list<unknown>`, `"filter" => arg`,
`"fold" => Unknown`; `apply` falls through to the default `Unknown`). So even
with a fully-typed lambda:

- `std-fold` — `fold(Fn {acc: s64 x: s64} add(acc x) 0 [1 2 3 4 5])` → still
  fails (fold's result node is `Unknown`).
- `std-apply` — `apply(Fn {a: s64 b: s64} add(a b) {a: 20 b: 22})` → still
  fails.

**Bucket C — intentionally-heterogeneous list return; a small example rewrite
fixes it, no checker work (2).**

- `eval-fn-by-name`, `eval-fn-by-order` — the body is `[path force]`, a
  `[string, bool]` list. With typed params these change from "cannot infer" to
  "`heterogeneous list: elements must share one type`". Returning a **record**
  (`{path: path force: force}`) passes strict — verified. The examples teach
  call-by-name vs call-by-order, which a record return still demonstrates.

**Bucket D — needs deeper checker/backend work; cannot be rewritten away without
abandoning what the example teaches (7).**

- `eval-twice` — higher-order *user* def `Def twice Fn {f x} f(f(x))`. Even
  `Def twice Fn {f: Fn {x: s64} s64  x: s64} f(f(x))` → still fails: indirect
  application of a function-typed **parameter** (and passing a `Fn` literal as
  an argument) isn't typed the way a function-typed *local* is. Needs the
  checker to type application through arrow-typed params / expected-arrow
  propagation into argument lambdas.
- `sf-fn-adder` — `adder` returns a **capturing** closure (`Fn {n} add(n by)`).
  Typing the params still fails: typing a returned capturing `Fn` literal as a
  concrete arrow is exactly the not-yet-landed 5.8 "Fn-literal capture" slice.
- `eval-apply-list` — `apply(get(ops 1) 21)` over `[Fn … Fn …]`: a list of
  function values, indexed then applied. Needs list-of-functions typing (the
  multi-case variant/dispatch 5.8 slice) plus a typed `apply`.
- `tail-count-down`, `tail-sum-to` — self-recursive defs. Typing every param
  still fails, because the def's result type can't be inferred through the
  recursive call, and **there is no result-type annotation syntax** on `Fn`:
  `Fn {n: s64} s64` parses `s64` as the *body* ("unbound name `s64`"). Needs
  recursion-aware result inference (fixpoint) or a new result-annotation form.
- `std-cells` — `cell-new/get/set` have no static cell type; `cell-set` is typed
  `Unit`, `cell-new` is untyped. `Let {c: The cell(s64) cell-new(0)} …` still
  fails. Needs a static cell type in the checker (3.9's own "category b").
- `macro-trylet` — the macro expansion contains an option-typed hole pattern;
  typing `parse`'s param doesn't help (3.9's "category c").

Totals: A=6, B=2, C=2, D=7 → 17. ✔

### The load-bearing consequence

**No pure-rewrite path reaches the green gate.** Buckets B and D (9 examples)
cannot be fixed by adding types to the source — fold/apply return `Unknown`
regardless, recursion has no annotation, cells/macro-trylet/capturing-closures/
lists-of-functions need checker or backend support. So the real decision is
**not** "inference vs rewrites for everything." Checker/backend work is
mandatory for ≥9 of the 17 either way. The genuine choice is a **pedagogy** one,
over the ~6 mainstream higher-order examples in bucket A: do they stay untyped
(inference) or get explicit types (rewrites)?

## 2. The question

**How do we clear the 17-example strict backlog so `--strict` can become the
default — and specifically, for the mainstream higher-order examples, do we
infer untyped lambda params from the call site (keeping the docs' untyped
teaching) or rewrite the examples with explicit types?**

---

## 3. Options and tradeoffs

### (a) Expected-arrow-directed param inference + typed higher-order builtin sigs

Give `map`/`filter`/`fold`/`apply` parametric arrow signatures in `check.rs`, and
have the checker push the expected arrow onto an untyped `Fn` literal's params at
the call site (bidirectional typing into the `fn`-macro), so
`map(Fn {x} mul(x x) …)` types `x` from `map`'s signature. Extend the same
expected-arrow propagation to user-defined higher-order params so `twice`
resolves.

- **Clears (verified/derivable):** bucket A (map-square, std-map, std-filter,
  eval-fn-scalar) *and* bucket B (std-fold, std-apply) with the examples staying
  **as-authored and untyped**. `eval-twice` clears only if the propagation is
  extended to user-def params (harder than the builtin case).
- **Does NOT clear on its own:** pm-none (no expected arrow — needs ascription),
  and all of bucket D except eval-twice (recursion, cells, macro-trylet,
  capturing-closure adder, list-of-functions apply-list) — each needs its own
  treatment.
- **Semantics/pedagogy:** best preserves the docs — the "untyped lambda" style
  the examples currently *teach* keeps working under strict; nothing in the
  teaching corpus has to spell types it didn't before. This is the only path
  that doesn't change what the docs teach.
- **Cost/blast-radius:** highest checker cost. Bidirectional param inference and
  parametric builtin arrows are a real feature (touches the `fn`-macro checking
  path, builtin result typing, and `check_indirect_apply`). Blast radius is the
  checker only; no example churn, so no `regen-examples`.

### (b) Typed rewrites of the documented examples (no checker changes)

Rewrite the 17 with explicit param types; re-lock via `regen-examples`.

- **Reality check (verified):** this **cannot reach the gate.** Buckets B and D
  (9 examples) still fail with explicit types — fold/apply return `Unknown`,
  recursion has no annotation syntax, cells/macro-trylet/adder/apply-list need
  checker or backend support. Option (b) "no checker changes" is *insufficient*
  on its own; taken literally it leaves the flip permanently blocked.
- **Where it does apply:** bucket A becomes typed one-liners, and bucket C is a
  clean record-return rewrite. But that is only 8 of 17.
- **Semantics/pedagogy:** heaviest on the docs — every higher-order example
  grows explicit param types, changing the teaching style toward "always spell
  your lambda types." Some reviewers prefer this (it advertises the type
  system); it's a values call.
- **Cost/blast-radius:** smallest *checker* cost for the 8 it can fix, but forces
  `regen-examples` (examples.json + committed playground wasm) and doc-prose
  edits, and **still** requires all the bucket-B/D checker work — so as a
  standalone answer it doesn't exist.

### (c) Hybrid — inference for the mainstream cases, targeted work for stragglers (RECOMMENDED)

Do the option-(a) inference + typed builtin sigs for the mainstream higher-order
examples (buckets A+B, kept untyped), a small record-return rewrite for bucket C,
and straggler-specific checker/backend work for bucket D:

- recursion result inference (or a `Fn` result-annotation form) → tail-count-down,
  tail-sum-to;
- a static cell type → std-cells;
- the option-typed hole in macro expansion → macro-trylet;
- the remaining 5.8 slices already on goal 5's docket (Fn-literal capture typing;
  multi-case variant/dispatch for lists of functions) → sf-fn-adder,
  eval-apply-list, and eval-twice's user-def application.

- **Why recommended:** it matches the verified reality — checker/backend work is
  unavoidable for ≥9 examples, so the only question left is pedagogy for the ~6
  mainstream ones, and inference there keeps the docs' untyped teaching intact
  (honouring 3.9 rider (a): the corpus stays strict-clean without being
  rewritten into a different style). Several stragglers (adder, apply-list,
  eval-twice) are cleared *for free* by 5.8 slices already planned for goal-5
  session 15, so the incremental cost is recursion inference + cell type +
  macro-trylet, plus the builtin-sig/inference work.
- **Cost/blast-radius:** the union of (a)'s checker work and the targeted
  straggler fixes, plus one small example rewrite (bucket C) needing
  `regen-examples`. Sequences naturally behind the in-flight 5.8 work.

### (d) Flip with a documented escape hatch (examples run non-strict / per-file pragma)

Flip the default now and let the 17 stragglers run under an escape hatch (a
per-file `gradual` pragma, or running the example suite non-strict).

- **Against the recorded plan:** 3.9's accepted gate is *objective green* and its
  rider (b) is to **delete** gradual mode on flip precisely so no second dialect
  survives ("quietly undoes 2.2.6"). A pragma/escape hatch is a second dialect by
  another name — it is **not** contemplated by the recorded 3.9/3.10 plans; it
  contradicts them.
- **Cost/blast-radius:** low up-front, high long-term — totality (goal 3's whole
  point, and goal 5's "gradual → total" premise) is never actually reached; the
  ABI-native backend (goal 5) still has to carry the boxed fallback for anything
  the hatch admits. Represented here for completeness as a *new* alternative, not
  recommended.

### Recommendation

**(c) Hybrid.** The verification forces it: pure rewrites (b) can't reach the
gate, and pure inference (a) leaves the non-lambda stragglers unaddressed. Do
inference + typed builtin sigs for the mainstream higher-order examples (keeping
them untyped, per 3.9 rider (a)), a record-return rewrite for the two
call-convention examples, and finish the straggler-specific checker/backend work
— much of which (capturing-closure and list-of-function typing) is already on
goal-5's docket. If you'd rather the docs *advertise* types everywhere, answer
"(c) but type the bucket-A examples explicitly" and we drop the inference piece
in favour of rewrites for those six while keeping all the straggler work.

## 4. What to do once answered (per-option implementation plan)

Common to every option — **the flip itself, once backlog = 0** (per 3.9/3.10):
1. Make strict the default: default `STRICT` to true and remove the opt-in
   branch in `src/main.rs` (lines 9-11) and the `--strict` help line; then delete
   gradual mode — the `Type::Unknown`-as-top code paths in `check.rs` and the
   boxed-fallback branches that exist only to serve them — so `Unknown` is
   *always* an error (3.9 rider b).
2. Finish 3.10's parked example sweep (any last examples that only made sense
   under gradual), and confirm every new example is strict-clean (3.9 rider a).
3. Confirm the conformance suite passes under strict (the second half of the
   option-1 gate).

**Verification gates (all options):**
- `cargo test` — all suites, including `tests/differential.rs` (oracle↔backend)
  and `tests/examples.rs`.
- `tests/strict_mode.rs::strict_backlog` must print **0 of 86**. It's currently a
  *diagnostic*, not a hard gate; consider converting it to an assertion (fail if
  the backlog is non-empty) at flip time so it ratchets.
- `tests/differential.rs` `SKIP` list (line 50): shrink it as examples become
  expressible; the harness already fails if a SKIP-listed example starts
  agreeing (line 267), so stale entries can't linger.
- `CHANGELOG.md` `## [Unreleased]`: record the strict-default flip and

- Docs prose: `docs/docs/language/type-system.mdx` (the "Function values"
  section, already present), plus `philosophy.mdx` / `pattern-matching.mdx` /

- LSP: diagnostics flow through the shared checker automatically (session 14
  confirmed), so the new hard errors surface for free — but re-run the LSP tests
  (4/4) after the flip. No grammar/`wavelet.nvim` change: the flip touches no

**Option (a) — inference + typed builtin sigs:**
- `src/check.rs`: replace the hard-coded `Unknown` results for the higher-order
  builtins (lines 2404-2406 and the `apply` fall-through) with parametric arrow
  signatures — `map: (a) -> b` over `list<a>` giving `list<b>`, `filter`, `fold`,
  `apply` likewise — reading the element/arrow types from the argument nodes.
- Add expected-arrow propagation: when checking a call argument position whose
  builtin/def signature expects an arrow, thread that arrow as the `expected`
  type into the argument `Fn` literal so its untyped params take the expected
  param types (extend the `fn`-macro checking path and `check_indirect_apply`).
  Extend to user-def higher-order params to clear `eval-twice`.
- Tests: new `tests/type_system.rs` cases for each builtin arrow and for
  expected-arrow param inference; `strict_mode` positive cases for the
  now-untyped-but-accepted examples. **No `regen-examples`** (examples unchanged),
  except pm-none, which still needs an ascription or a Match-scrutinee-expected
  rule — decide which and, if the example text changes, run `regen-examples`.
- Still owes the bucket-D straggler work (below) to actually reach 0.

**Option (b) — typed rewrites:**
- `docs/scripts/gen-examples.mjs`: add explicit param types to bucket A, and
  record-return rewrites to bucket C. (This gets you to 8/17.)
- You **must still** do the bucket-B and bucket-D checker/backend work — there is
  no rewrite for fold/apply's `Unknown` result, recursion result inference, cell
  types, macro-trylet, capturing closures, or lists of functions. Treat "(b)" as
  "(c) with the bucket-A examples typed explicitly."
- Run `./scripts/regen-examples.sh` (rebuilds `docs/examples.json` + the
  committed playground wasm, re-locks `cargo test`). Update doc prose to match
  the now-typed examples.

**Option (c) — hybrid (recommended):**
- Inference + typed builtin sigs exactly as in (a), for buckets A+B (examples
  stay untyped).
- Bucket C: record-return rewrite in `gen-examples.mjs`; `regen-examples`.
- Bucket D straggler work:
  - **Recursion** (tail-count-down, tail-sum-to): recursion-aware result
    inference in `check.rs` (type the def's result via a fixpoint over the
    recursive call), or add a `Fn` result-annotation form (currently
    `Fn {n: s64} s64` mis-parses `s64` as the body — a reader/`form.rs` change if
    you go this way). Prefer inference to avoid new surface syntax.
  - **Cells** (std-cells): a static cell type in `check.rs` — type `cell-new(x)`
    as `cell<T>`, `cell-get` as `T`, `cell-set` as `Unit` (already), and admit a
    `cell(T)` ascription in type position.
  - **macro-trylet**: type the option-typed hole in the post-expansion check
    (3.9 "category c" — re-derive at flip time).
  - **sf-fn-adder, eval-apply-list, eval-twice's user-def application**: the
    remaining 5.8 slices already on goal-5 session-15's docket — `Fn`-literal

    duplicating it.
- `regen-examples` once (bucket C changed); the rest is checker/backend with unit

**Option (d) — escape hatch (if chosen despite the recommendation):**
- Add a per-file `gradual` pragma or a non-strict example-suite mode; document it
