**Proposal 2 of 2 (from the interp.rs review): reject float literals as Match patterns.**

`match_pattern` (interp.rs) accepts a `Dec` literal pattern and matches it by f64 equality. Float equality patterns are a classic footgun (`0.1 + 0.2` never matches `0.3`; a `nan` pattern matches nothing, ever), and once 3.12 exhaustiveness lands they are dead weight: no set of float literals can ever be exhaustive, so every such Match needs a catch-all anyway.

**Question: does a float literal in pattern position become a compile error?**

Options:

1. **Reject at check time (recommended).** A `Dec` literal pattern is a checker error pointing at an explicit comparison (`If eq(x 0.5) ...` or a guard, when guards exist). Int/bool/char/string literal patterns are unaffected — their equality is exact.
2. **Keep, documented as exact-bits equality.** Zero migration cost, but it preserves a pattern form that is almost always a latent bug and that exhaustiveness checking can never bless.

Recommendation: **option 1**, sequenced with 3.12 (it is one line in the same checker pass that learns pattern types). Until then the runtime behaviour stays as-is; nothing in the examples or conformance suite uses a float pattern today.
