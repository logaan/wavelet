**Proposal 1 of 2 (from the interp.rs review): drop list-payload positional binding at calls.**

Today `bind_params` (interp.rs) binds an n-parameter function from a *single list argument* of length n exactly as it would from a tuple: `f(xs)` where `xs = [1 2]` and `f = Fn {a b} ...` binds `a=1, b=2` positionally. The same clause also accepts an empty list/record/flags value as "no arguments" to a 0-parameter function.

**Question: does a list argument stop binding parameters positionally, so only tuples (and by-name records) destructure across parameters?**

Options:

1. **Drop it (recommended).** A single list argument is one value, bound to one parameter like any other value; positional multi-binding is the tuple's job, by-name binding the record's. Under 2.2.1 a list is `list<t>` — binding differently-typed parameters from one is unrepresentable anyway, and for same-typed parameters it silently couples arity to a runtime length (an n-1-element list is a runtime bind error today, a compile-time nothing). The empty-list/flags/record "no arguments" acceptances go with it; `()` is the empty tuple and suffices.
2. **Keep it.** Saves writing a destructuring `Let`/`Match` in the rare list-of-known-length case, at the cost of a second, length-dependent meaning for "call f with one list".

Recommendation: **option 1**, landing with the 3.9/3.10 strict burn-down (it is the same family as the 2.2 drops: a runtime shape-dispatch the checker cannot see). Interpreter first, then backend, per the oracle rule.
