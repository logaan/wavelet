# Shebang script execution only recognizes .wlt-suffixed files

## What

Shebang / bare-file script execution is dispatched by `is_script_path`
(`src/main.rs:39,65-67`), which returns true **only** when the first CLI
argument ends in `.wlt`:

```rust
fn is_script_path(arg: &str) -> bool { arg.ends_with(".wlt") }
```

## Why it matters

bug-risk / DX: the documented use is `#!/usr/bin/env wavelet` on an *executable*
script (`src/main.rs:33-38`). Unix scripts are very commonly **extensionless**
(e.g. an executable named `deploy`, no suffix). The kernel then invokes
`wavelet /path/to/deploy`, `is_script_path("deploy")` is false, and the program
falls through to the usage error (`src/main.rs:40-53`) instead of running the
script. So shebang support silently only works for files that happen to keep the
`.wlt` extension — which defeats much of the point of making a `.wlt` file
directly executable.

## Suggested change (sketch)

Broaden the guard without shadowing the bare-word subcommands: treat the first
arg as a script when it is **not** one of the known subcommands *and* names an
existing readable file (optionally also sniff a leading `#!` first line, which
the lexer already skips — goal 7.2). E.g.:

```rust
fn is_script_path(arg: &str) -> bool {
    !KNOWN_SUBCOMMANDS.contains(&arg) && std::path::Path::new(arg).is_file()
}
```

Keep `.wlt` as a fast-path. Add a `tests/shebang.rs` case for an extensionless
executable script.

## Severity / effort

bug-risk / S.
