# Interpreter neg and abs are unchecked while binary arithmetic is checked

## What

In `src/builtins.rs`, `neg` and `abs` use unchecked Rust operators while the
binary arithmetic ops are checked:
- `neg` → `Value::Int(-n)` (`src/builtins.rs:401`)
- `abs` → `Value::Int(n.abs())` (`src/builtins.rs:405`)
- vs `add/sub/mul/div/rem` → `i64::checked_*` with the error "integer overflow
  or division by zero" (`src/builtins.rs:305,366-382`).

`-n` and `i64::abs` **panic on overflow in debug builds** and **wrap in release**
for the single input `n == i64::MIN` (-9223372036854775808). The wasm backend's
`neg` is documented as "wrapping 0 - x" (`src/emit.rs:6150-6153`) and wraps.

## Why it matters

- Interpreter self-consistency: `neg`/`abs` violate the checked-arithmetic
  contract the other five ops uphold — `neg(i64::MIN)` **aborts the interpreter
  process** in a debug build (panic), rather than returning a catchable
  `eval error` like `add(i64::MAX, 1)` does.
- Oracle divergence: in release the interpreter wraps and the backend wraps, so
  they agree on a value; but the *interpreter's own* contract ("overflow is an
  error") is broken, and debug-vs-release behaviour differs. It is a narrow input
  but a genuine inconsistency in the semantics oracle.

## Suggested change (sketch)

Route `neg`/`abs` through the same checked path: `n.checked_neg()` /
`n.checked_abs()` returning the same "integer overflow" error on `None`. Then
decide the backend's matching behaviour (trap) so both agree on *failing* rather
than silently wrapping — or explicitly document wrap-on-overflow for unary ops
as the intended semantics and make both wrap deterministically (drop the debug
panic). Either way, unary and binary integer overflow should behave the same.
