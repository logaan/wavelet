## Context
The biggest payoff in 5.6 (compound builtins over canonical layouts) is building
canonical, unboxed records/variants/flags DIRECTLY in bare exported function
bodies (the "export fast-path"). For a construction site inside a body to know the
target canonical layout, the checker must thread the function's DECLARED RESULT
TYPE into its body. Today `check_roots` checks Fn bodies with `expected = None`, so
that type never reaches the body. Session 7 implemented the threading (it works)
but reverted it because it surfaces three coupled semantics questions. Deciding
these is the precondition for 5.6 being sound.

## The decision (one call, three facets)
Thread the declared result type into function bodies? And if so:

1. **Boundary int-widening (the crux).** With the result type threaded in, the
   checker's `unify` rejects a body that produces a NARROWER int than the declared
   result (e.g. an s32-typed body for an s64 result) — this broke 8 existing
   backend_lists tests, because programs currently rely on int width being
   unchecked in bodies. The interpreter (the oracle) doesn't distinguish int
   widths at runtime, so these programs run fine; only the stricter checker
   objects.
   - Option A (my recommendation): **allow safe widening** — a narrower int may
     flow to a wider declared result of the SAME signedness; still reject
     signed↔unsigned mixing and wider→narrower. Matches the interpreter, preserves
     existing programs, and is the standard "widening is safe, narrowing needs an
     explicit op" rule.
   - Option B: require exact width match; make the 8 programs insert explicit
     conversions. More explicit, but breaks working code and diverges from the
     oracle.

2. **Return-type-directed overload resolution in bodies.** Threading the result
   type also lets the checker resolve overloads inside the body using it — a
   runtime-behavior change. It's consistent with the memoised return-type-directed
   resolution already in check.rs (flagged in the 2.1 review). My recommendation:
   **allow it**, verified against the interpreter.

3. **New sub-expression type errors.** Threading `expected` down can surface real
   type mismatches in sub-expressions that were previously unchecked. My
   recommendation: **accept them** (they're genuine), after confirming the full
   example + conformance suite still passes (which facet 1 covers).

## My recommendation in one line
Thread the declared result type in; allow safe same-signedness int widening
(Option A); allow return-type-directed resolution in bodies; accept new legitimate
errors — all validated against the interpreter oracle and the full test +
conformance suite before landing.

If you're happy with that, a "yes to all / Option A" is enough and I'll schedule
it as the first item of the next goal-5 session (before 5.6). If you want a
different call on any facet, say which.
