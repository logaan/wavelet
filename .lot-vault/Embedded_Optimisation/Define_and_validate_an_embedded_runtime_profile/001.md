# Define and validate an embedded runtime profile

Choose concrete embedded targets and a runtime deployment path before advertising embedded readiness. Core Wasm support alone does not imply Component Model support. Historical research found Wasmtime no_std/AOT/Pulley as one candidate, and unresolved direct component support in WAMR; reverify current versions during implementation.

Specify target CPU/OS, interpreter versus AOT, required instructions/proposals (including tail calls and bulk memory), maximum memory, stack, permitted host capabilities, startup and failure behaviour. Compile macros and the Wavelet compiler off-device. Keep Component Model artifacts as normal outputs; investigate a core-Wasm or statically linked deployment only with explicit bindings and resource semantics.

Acceptance: at least one named board/runtime runs representative components and reports firmware flash/RAM, guest memory, startup/latency and limits; unsupported features fail at build time; small devices have a supported no-growth/budgeted configuration. Hard real-time claims require worst-case resource/timing evidence, not merely successful execution.
