Clarification: map and fold need no builtin-name special cases or intrinsic compiler support. Both should be explicitly imported library definitions.

Macro-first is a valid, potentially smaller first implementation. Library compile-time macros can expand to ordinary loops or tail recursion, typed element operations, builder operations and callback expressions. The compiler then checks and compiles the expansion using general language facilities. Expansion must use hygienic/fresh bindings, evaluate sequence/callback/initial-value expressions exactly once as required, preserve source evaluation order and capture semantics, and retain useful diagnostics. Coordinate with the compiled-macro pipeline; no interpreter runtime should be introduced into emitted programs.

An alternative is ordinary generic library functions with compile-time callback specialisation and inlining. This can produce the same direct loops while giving a cleaner typed function API. It needs general cross-module generic/callback specialisation, not compiler knowledge of the names map or fold. Choose this path when the extra compiler facility benefits generic libraries broadly. A macro-first implementation does not require completing all of this generic-function machinery first.

These alternatives supersede any reading of the original milestone/dependency list that requires first-class map/fold support or mandatory generic-function specialisation before migrating map/fold. The source-library distinction remains: compile-time imports must place expanded/specialised code in the caller, without runtime component ABI calls per operation or per element. Existing macro-component imports may provide the initial compile-time delivery mechanism; introducing a new source-module import spelling is a design proposal rather than a prerequisite for proving macro-based map/fold.

First slice acceptance: an explicit library import provides map and fold as macros or generic definitions; no builtin registry entry/emitter dispatch remains for those names; emitted code contains direct loops/callback code, no dynamic closure allocation and no canonical ABI hops; ordinary map still allocates its result when its semantics require one. Tests cover evaluation-once, captures/name collisions, callback effects, trap order and equivalent typed output.

Fusion is separate. Expanding map and fold independently still ordinarily constructs the intermediate list. A library iterator/fold-producer pipeline can compose transformations before a terminal fold and specialise the pipeline away, or general compiler allocation/loop optimisations can fuse eligible eager code. Neither macro expansion nor function inlining alone guarantees fusion. Preserve eager evaluation/effect/trap semantics, or make different streaming semantics explicit in the library API.
