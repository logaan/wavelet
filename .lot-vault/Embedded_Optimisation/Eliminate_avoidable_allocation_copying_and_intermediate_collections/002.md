Clarification from the standard-library design discussion: fusion must work on general emitted code or an explicit library pipeline protocol, without special recognition of builtin names map/fold. Library operations may initially be compile-time macros that emit ordinary loops/recursion and callback expressions, or generic functions whose static callbacks are specialised and inlined. Both are valid sources of optimisation opportunities.

Independent macro expansion or inlining of eager map followed by fold still materialises the mapped list unless another transformation removes it. Two supported approaches to investigate are (1) an explicitly streaming iterator/fold-producer library representation specialised away at the terminal operation, and (2) general escape/allocation/loop analysis of eager code.

Do not equate eager and streaming evaluation for effectful callbacks. Eager map completes all mapping calls before fold callbacks begin; a fused streaming loop interleaves them. Traps and allocation failure can also be observed at different points. Require proof that reordering is unobservable before fusing an eager pipeline, or require an explicit streaming API whose order is part of its contract. Preserve argument evaluation-once and capture/aliasing semantics in macro expansions.

Acceptance additions: show an eligible pure pipeline without intermediate allocation; show effectful or trapping eager cases preserving original order or declining fusion; show explicit streaming pipeline order independently. Report whether gains came from macro staging, generic specialisation, inlining, or actual allocation/fusion optimisation. No claim of automatic fusion solely because map/fold moved into macros.
