# Macros

A macro receives unevaluated source forms and returns a replacement form during compilation. Because code has a data representation, a macro can inspect and construct it using ordinary operations on forms.

## Macros as components

A macro library exports `wavelet:meta/macros@0.1.0`. Its manifest lists macro names and arities; its expansion operation transforms a tree of forms. A library can be written in any language that implements this WIT interface.

### Importing a macro library

Use `macros: true` and supply the executable component:

```wavelet
Import {pkg: "acme:html/dsl" macros: true from: "vendor/dsl.wasm"}

Export {name: page params: {title: string} result: string}
Def page Fn {title: string} Element "h1" title
```

A macro-only import runs during compilation and does not become a runtime import of the emitted component. The library is selected with `from:`, or found at the conventional `wit/macros/<namespace>-<package>.wasm` path. For `acme:html`, that path is `wit/macros/acme-html.wasm`.

One declaration can expose both a runtime interface and macros:

```wavelet
Import {pkg: "demo:library/api" as: lib roles: {runtime macro}
        from: "vendor/library-macros.wasm"}
Def answer Fn {} lib/Identity lib/increment(41)
```

Here `Identity` expands during compilation and `increment` is a runtime call. `roles: {macro}` is equivalent to `macros: true`; `roles: {runtime}` is an ordinary import. Combining `roles` with `macros`, or supplying empty or unknown roles, is an error.

Projects supply executable macro artifacts explicitly. Automatic registry fetching of macro components is not a goal. WIT dependency resolution describes interfaces and is separate from acquiring executable macro code.

### The `wavelet:meta/macros` interface

```wit
interface macros {
  use code.{tree};
  manifest: func() -> list<tuple<string, u32>>;
  expand: func(name: string, args: tree) -> result<tree, string>;
}
```

`manifest` returns name/arity pairs. `expand` receives a macro name and argument forms, then returns a replacement form or an error message. The tree uses a flat node table and a root index, allowing source forms to travel through WIT without recursive interface types. Expansion repeats until no further macro replacement applies.

### Writing a macro library in Wavelet

A source containing a `Package` and only `DefMacro` declarations compiles as a macro library:

```wavelet
Package "acme:html@0.1.0"

DefMacro element {tag body}
  Quasi str-cat("<" Unquote(tag) ">" Unquote(body) "</" Unquote(tag) ">")

DefMacro unless {condition body}
  Quasi If Unquote(condition) "" Unquote(body)
```

```console
$ wavelet build html.wlt -o out
```

Use the emitted `out/acme-html.wasm` as the importing file's `from:` artifact, or place it in `wit/macros/acme-html.wasm`. The `Element "h1" title` consumer above then expands into ordinary string concatenation. This small example constructs markup directly; an application handling untrusted text should escape it before inserting it into HTML.

### Qualifying and aliasing

Imported macros have bare and prefixed spellings. With alias `dsl`, `Element`, `dsl/Element`, and `dsl-Element` refer to the same imported macro when unambiguous.

If two libraries or a local macro supply the same bare name, qualify the call:

```wavelet
Import {pkg: "acme:html/dsl" as: html macros: true}
Import {pkg: "acme:svg/dsl" as: svg macros: true}

html/Element "h1" title
svg/Element "circle" attrs
```

An ambiguous bare name is rejected when used. Qualified names select the intended library.

### Macros in the browser

The browser compiles local macro definitions into components and instantiates them before expansion. To import a prebuilt macro library, supply its bytes through the [browser REPL's dependency inputs](../browser-repl#dependencies-and-macros). Macro methods are synchronous; loading and instantiation happen before the compiler invokes them. See [Compiler API](../compiler-api#macro-preparation) for the embedding protocol.
