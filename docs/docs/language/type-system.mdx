# The type system

Wavelet is **statically typed**. Every expression has exactly one
[WIT](https://component-model.bytecodealliance.org/design/wit.html) type, decided
before any code runs. The compiler runs a checker pass over your whole program on
every path — `wavelet run`, `wavelet build`, `wavelet wit`, and the playground —
and an ill-typed definition is a **compile error even if nothing calls it**.
There is no runtime type error to discover at the wasm boundary — if it builds,
it is well-typed.

The system is **monomorphic**: there are no type variables in the language you
write or in the WIT it produces. Generics live entirely at compile time
(`Derive`, functors), and what ships is always concrete.

## Two rules

Checking is **bidirectional**, which is just two rules working together:

1. **Synthesis** — some expressions tell you their own type. An atom
   (`true`, `'x'`, `"hi"`), a bound name, or a call all *produce* a type from the
   bottom up.
2. **Checking** — some positions *expect* a type, and push it inward. A function
   parameter's declared type, a `Let` binding, the branches of an `If`, and the
   clause results of a `Match` all flow an expected type down into the
   sub-expression.

Two consequences fall straight out of "every expression has exactly one type":

- The branches of an `If` must share a type — `If b 1 "s"` is rejected, because
  an `s64` and a `string` have no common WIT type.
- The result clauses of a `Match` must likewise all unify to one type.

Because checking is **total**, names are resolved statically too: an unbound name
or a wrong-typed use inside a never-called function is still a compile error.

## Numeric literals and `The`

A bare numeric literal has no fixed type on its own — it takes its type from
context and is **range-checked** against it. `100` is a fine `u8`; `300` is not:

<Playground id="sf-the-bad" />

When there is no context to resolve a literal, it **defaults**: integer literals
default to `s64`, fractional literals to `f64`.

The `The` form ascribes a type to an expression. Use it to pin a literal's type,
to drive a range check, or — as you'll see below — to choose between overloads by
the result you want:

<Playground id="sf-the-ok" />

A literal that cannot fit the ascribed type is a compile error (`The u8 300`,
`The u8 -1`, `The s32 1.5` are all rejected).

## Declared result types

The `result:` type in an `Export {…}` form flows into the exported function's
body as its expected type, exactly as an enclosing `The` would: construction
sites build at the declared shape, and the body is checked against the declared
result. A body whose type genuinely conflicts with what the export promises is a
compile error rather than a silent coercion.

Two coercions the component boundary genuinely performs stay legal. A narrower
integer result may **widen** into a wider declared result of the *same*
signedness — an `s32`-typed body satisfies an `s64` result — but mixed
signedness (`s32` into `u32`) and *narrowing* (`s32` into `s16`) are rejected. A
value carrying a `result` payload may also flow into a declared payload-less
`result`, since the ABI drops the payload: the `wasi:cli/run` entry point
`run: func() -> result` is satisfied by an `ok(0)` body.

## Overloading

Several `Def`s sharing a name form an **overload set**. Each call site is
resolved statically, first by the WIT types of its arguments:

<Playground id="ty-overload-int" />

Resolution doesn't depend on definition order — the other member is just as
reachable:

<Playground id="ty-overload-str" />

When the arguments don't decide (for instance, two zero-argument members), the
**expected return type** breaks the tie. Supply it with `The`:

<Playground id="ty-the-return" />

With neither arguments nor an expected type to disambiguate, the call is
**ambiguous** and is a compile error — you fix it by adding a `The`.

WIT has no overloading, so an *exported* overload set is **name-mangled at the
component boundary**: each concrete member gets a distinct export. An `eq` over a
`point` type, for example, is exported as `eq-point`.

A call that has no matching overload at all is simply ill-typed, even when it sits
in an uncalled function:

## Function values

A `Fn` literal whose parameters (and inferred result) all have concrete WIT
types carries a **function type** of its own — an arrow like `(s32) -> s32`. A
bare reference to a `Def`-bound function with such a signature is a first-class
value of the same arrow type. Applying a function-typed binding is statically
checked against its arrow: the arity and every argument type must match, and
the application synthesizes the arrow's result type.

```wavelet
Def inc Fn {n: s32} add(n 1)
Let {f: inc} f(41)      // f: (s32) -> s32, so this is 42
```

A `Fn` whose parameters are untyped has no concrete arrow — it stays a gradual
function value, exactly as before. (Higher-order stdlib functions like `map`
and `filter` accept either.)

Function types are **component-internal**: WIT has no function type, so a
function value cannot cross a component boundary. Exporting a function whose
result is (or contains) a function value is a compile error with a deliberate
diagnostic — *function types cannot cross component boundaries yet; import the
combinator as a macro so it expands into this component instead*. Sharing
behaviour **across** components is what [macro imports](macros.mdx) are for:
the combinator's *form* travels, and expands into each consuming component.

## Derive

`Derive` generates the standard operations for a type so you don't write the
boilerplate by hand. It takes a set of derivers and a type, and expands — at
compile time — into ordinary monomorphic definitions:

```wavelet
DefType point {x: s32 y: s32}
Derive {Eq Ord Show} point
```

This produces concrete operations specialized to `point` (an `eq` and a `show`
for `point`, an ordering comparison, and so on). The available derivers are
`Eq`, `Ord`, `Show`, and `Hash`. Because the generated definitions are just
ordinary overload-set members, exporting them mangles their names exactly like
any other export (`eq-point`, `show-point`, …).

`Derive` is a file-level macro: it runs during compilation of a component, not in
the interpreter playground.

## Functors

A **functor** specializes a generic data structure to a concrete element type at
compile time. You apply one with the dedicated `Instantiate` form, naming the
package, passing the functor's parameters *by name* in `with:`, and choosing a
local alias (`Import` stays what it is — bringing an unparameterized dependency
into scope):

```wavelet
Instantiate {pkg: "wavelet:coll/set" with: {elem: point} as: pts}
```

This synthesizes a **concrete, per-element WIT interface** — instantiating `set`
at `point` yields a `point-set` interface. Nothing generic survives into the
emitted world: a second instantiation at, say, `string` would produce a separate
`string-set` interface. WIT cannot write `resource set<t>`, so the functor writes
the monomorphic interface for you, once per element type you ask for.

The instantiation also brings the functor's operations into scope, qualified by
the alias. For the `set` functor these are `pts/new`, `pts/add`, `pts/contains`,
and `pts/size`, with exactly the signatures the synthesized resource promises:

```wavelet
Let {s: pts/new()}              // new() -> set        (an empty set)
  Do [ pts/add(s p)             // add(set, elem)       (returns unit)
       pts/contains(s p)        // contains(set, elem) -> bool
       pts/size(s) ]            // size(set) -> u32
```

`new()` hands back a fresh, mutable set; `add` mutates it in place and is a no-op
for an element already present (membership uses the same equality `Derive {Eq}`
gives the element type); `contains` and `size` observe it. These run under
`wavelet run` and the playground today.

:::note Building functors

`wavelet wit`, `wavelet run`, and now `wavelet build` all support functors. The
backend emits the synthesized per-element interface as a **real exported WIT
`set` resource**, at interpreter parity: any element type (primitive, string,
record, and compound list/tuple) works, and you can instantiate the functor
multiple times in one world. Membership uses the same structural equality the
interpreter does, so a built component dedups exactly like `wavelet run`.

The single limitation is shaping, not semantics: an export that *returns the
`set` handle* (`own<set>`) over a **local-record** element would make the
element's `api` interface and the resource's interface each `use` the other — a
WIT interface cycle, which WIT cannot express, so it is rejected with a clear
error. The buildable shapes are therefore (1) exports that derive an ordinary
result from the set (e.g. `-> u32`), and (2) handle-returning exports whose
element is a primitive or string.

:::

## Worked example: source to WIT

Putting it together — a derived record type and a `set` of it — and the WIT the
compiler synthesizes. The headline is that **nothing in the WIT is generic**:

```wavelet
Package "demo:geo@0.1.0"

DefType point {x: s32 y: s32}
Derive {Eq Ord Show} point

Instantiate {pkg: "wavelet:coll/set" with: {elem: point} as: pts}

Export nearest-set
Def nearest-set Fn {ps: list(point)}
  Let {s: pts/new()}
    Do [ each(ps Fn {p} pts/add(s p))
         s ]
```

synthesizes a world whose every signature is a concrete, ordinary WIT function or
type:

```wit
package demo:geo@0.1.0;

interface types {
  record point { x: s32, y: s32 }
}

interface api {
  use types.{point};
  eq-point: func(a: point, b: point) -> bool;
  compare-point: func(a: point, b: point) -> s32;
  show-point: func(v: point) -> string;
  nearest-set: func(ps: list<point>) -> point-set.set;
}

// the set functor, instantiated at `point`
interface point-set {
  use types.{point};
  resource set {
    constructor();
    add: func(value: point);
    contains: func(value: point) -> bool;
    size: func() -> u32;
  }
}

world geo {
  export types;
  export api;
  export point-set;
}
```

The derived operations and the export land in the `api` interface, while each
functor instantiation gets its own interface. The overload set `eq` lowers to
the distinctly named `eq-point`, the derived operations become concrete
functions, and the `set` functor becomes the concrete `point-set` interface. A
generic set would have wanted `resource set<t>` with `add: func(value: t)`,
which WIT simply cannot express — the functor produces a concrete interface
instead.

Note where `point` was declared: because `nearest-set` *returns* the `set`
handle, `api` needs the handle's type from `point-set` — and `point-set` needs
the element record. If `api` declared `point` itself, the two interfaces would
`use` each other, a cycle WIT cannot express. The compiler therefore **hoists**
the element record into a shared `types` interface that both sides `use`.
(A program whose exports only derive ordinary results — `-> u32` and friends —
keeps its record declarations in `api` as usual.)

(`each` here is illustrative iteration over the input list, applying `pts/add`
for its side effect; it is not yet a builtin. To run a set today, iterate with
`map`/`fold` or with explicit `pts/add` calls.)

## A program you can build

Every shape above builds — including `nearest-set`, which returns the `set`
handle over a record (the hoisted `types` interface is what makes that
expressible). Here are two more shapes shown with the WIT the backend actually
emits (run `wavelet build` then `wasm-tools component wit` on the result to
reproduce these verbatim).

### Derive an ordinary result

The simplest buildable functor program never hands the `set` back across the
boundary — it derives a plain value from it. Reusing the `point` set, an export
that counts distinct points returns a `u32`:

```wavelet
Package "demo:geo@0.1.0"

DefType point {x: s32 y: s32}
Derive {Eq Ord Show} point

Instantiate {pkg: "wavelet:coll/set" with: {elem: point} as: pts}

Export count-distinct
Def count-distinct Fn {}
  Let {s: pts/new()}
    Do [ pts/add(s {x: 1 y: 2})
         pts/add(s {x: 3 y: 4})
         pts/add(s {x: 1 y: 2})   // a structural duplicate of the first
         pts/size(s) ]
```

`wavelet build` emits a component whose `api` exports `count-distinct` as an
ordinary `u32` function; the `set` resource stays entirely inside the guest:

```wit
package demo:geo@0.1.0;

interface api {
  record point { x: s32, y: s32 }
  eq-point: func(a: point, b: point) -> bool;
  compare-point: func(a: point, b: point) -> s32;
  show-point: func(v: point) -> string;
  count-distinct: func() -> u32;
}

interface point-set {
  use api.{point};
  resource set {
    constructor();
    add: func(value: point);
    contains: func(value: point) -> bool;
    size: func() -> u32;
  }
}

world geo {
  export api;
  export point-set;
}
```

Calling `count-distinct` returns `2`: the two `{x: 1 y: 2}` points are
structurally equal, so the set dedups them — exactly the answer `wavelet run`
gives, because membership uses the same structural equality on both paths.

### Return the handle

An export can hand the `set` itself back as an `own<set>` handle for a host to
keep and query — over any element type (a local-record element just hoists the
record, as shown above; a primitive element needs no hoisting at all):

```wavelet
Package "demo:app@0.1.0"

Instantiate {pkg: "wavelet:coll/set" with: {elem: s32} as: ints}

Export build-ints
Def build-ints Fn {}
  Let {s: ints/new()}
    Do [ ints/add(s 1)
         ints/add(s 2)
         ints/add(s 1)            // duplicate; dedups away
         s ]                      // return the set itself
```

The emitted `api` returns the handle. Each functor interface names its resource
`set`, so the `use` is aliased (`set as s32-set-handle`) — which is also what lets
a single world instantiate the functor at several element types without the names
colliding:

```wit
package demo:app@0.1.0;

interface s32-set {
  resource set {
    constructor();
    add: func(value: s32);
    contains: func(value: s32) -> bool;
    size: func() -> u32;
  }
}

interface api {
  use s32-set.{set as s32-set-handle};
  build-ints: func() -> s32-set-handle;
}
```

A host calls `build-ints`, then invokes `size`/`contains` on the returned
resource (here `size` is `2`; `contains 1` and `contains 2` are true, `contains 9`
is false) and finally drops the handle to run the resource's destructor. This is
exactly what `tests/backend_functor.rs` does in-process against the wasmtime host
to prove the built component matches the interpreter — over `s32`, `string`,
`point` records, and `list` elements, and with two instantiations in one world.

## User-declared resources

A [functor](#functors) hands you a ready-made resource — the `set` above is one,
and so is a [`cell`](../stdlib#cells). `DefResource` lets you declare **your own**.
Where `DefType` introduces a *data* type (a record, variant, enum, or alias — a
value that is copied by structure across the component boundary), a resource is a
type with **identity and hidden state**: callers hold an opaque *handle*, never
the bytes behind it, and every use goes through the methods you declare. A
`DefResource` form maps one-to-one onto a WIT `resource { … }` block.

```wavelet
DefResource counter {
  New:   Fn {start: u32} cell-new(start)
  next:  Fn {self: counter} The u32 Do [ cell-set(self add(cell-get(self) 1))
                                          cell-get(self) ]
  value: Fn {self: counter} The u32 cell-get(self)
  sum:   Static Fn {values: list(u32)} The counter counter(fold(add 0 values))
}
```

### Members and their roles

The braces hold the resource's members. Two keys are **reserved and
capitalized**; everything else is a method or a static.

- **`New:` — the constructor.** It runs when the resource is created and returns
  **the representation** ("the rep"): an ordinary Wavelet value that holds the
  instance's private state. It is almost always a [`cell`](../stdlib#cells), since
  a resource without mutable state has little reason to exist. `New` is *anonymous*
  in WIT — a resource has exactly one constructor and it is unnamed.
- **`Drop:` — the destructor (optional).** An `Fn {self: <name>}` returning unit,
  run when a handle is dropped. It is **not user-callable** — the runtime invokes
  it — and if you omit it the rep is still freed; a `Drop` is only for extra
  cleanup (closing a handle you opened, say). Absent `Drop` means "no-op on drop."
- **`Static Fn {…}` — a static.** Marked with `Static` and taking **no `self`**, a
  static belongs to the type rather than to an instance. Because it can *return*
  the resource, a static doubles as an **alternative constructor** — `sum` above
  builds a `counter` from a list.
- **any other member — an instance method.** Its first field **must** be
  `self: <name>`, and inside the body `self` is bound to the rep. `next` and
  `value` read and mutate through `self`.

The checker enforces the discipline, and each violation is a compile error:

- a `Static` member that declares `self`;
- a non-static member (other than `New`/`Drop`) that lacks `self: <name>` as its
  first parameter;
- `Static` written on `New` or `Drop` (neither may be a static).

:::note[Why the `The` ascriptions]
`counter`'s rep is a `cell`, and neither `cell-get` nor the `counter(…)`
constructor call can be told the element type by structure alone — a bare `1` also
has no fixed type until context pins it (see [`The`](#numeric-literals-and-the)).
So each member result that flows through one is ascribed: `The u32` on the reads,
`The counter` on `sum`'s constructed result. A resource whose rep is a default-typed
`s64` cell can often drop them, but writing the ascription is the habit that keeps
resource members well-typed.
:::

### Calling a resource

At the use site a resource reads like the [`set`](#functors) functor's operations,
because the spellings are the same:

```wavelet
Def c counter(5)                 // the constructor: the type name, applied
Do [ counter/next(c)             // a method: `type/method(handle …)`  -> 6
     counter/next(c)             //                                    -> 7
     counter/value(c) ]          // -> 7
```

The **constructor is the type name applied** (`counter(5)`) — anonymous and
singular, matching WIT's unnamed constructor; extra ways to build one are statics.
**Methods and statics are qualified** by the type name: `counter/next(c)`,
`counter/sum([1 2 3 4])`. A method takes the handle as its first argument (the
`self` field); a static does not.

### Ownership at the boundary

In a type position a resource name carries an **ownership mode**, exactly as WIT's
`own`/`borrow` do:

- **`counter` (bare) — owned.** Ownership *transfers* to the callee, which is
  responsible for dropping it. `own(counter)` is the explicit synonym for the bare
  spelling.
- **`borrow(counter)` — borrowed.** The callee may use the handle but does not own
  it. `borrow` is **parameter-position only**: a borrow may not appear in a result
  or in a stored position (a record field, a list element), and doing so is a
  compile error.

Passing a handle to an **own** parameter *invalidates the caller's handle* — using
it again later **traps**. A **borrow** never invalidates: the caller keeps its
handle. This is WIT's linear-handle discipline surfaced in Wavelet.

Ownership modes only exist at the **component boundary**. Inside a method or static
body the type name denotes the rep — `self: counter` binds `self` to the `cell`, not
to a handle — so `own`/`borrow` never appear there.

### Identity, printing, and serialization

A resource is **not** a value with structure, and its observable behaviour reflects
that:

- **Equality is identity.** Two handles are equal only when they are the *same
  instance*; two independently constructed counters are never equal, even with
  equal state. Because there is nothing structural to compare, `Derive {Eq}` (or
  `Ord`, `Hash`, `Show`) over a resource type is a **compile error** — the derivers
  work on data, not handles.
- **`to-string` is opaque.** Printing a handle yields the token `<counter>` (the
  type name in angle brackets), never its state.
- **Not form-serializable.** A resource is not a form, so [`read`](../stdlib#conversion)
  can never produce one and a handle cannot be round-tripped through text.

```wavelet
eq(counter(1) counter(1))    // false — two distinct instances
to-string(counter(9))        // "<counter>"
```

### Exporting a resource

A bare [`Export`](./special-forms#export) publishes the whole resource as one WIT
`resource` block:

```wavelet
Export counter
```

The record form places it in a named interface:

```wavelet
Export {iface: "counters" name: counter}
```

A `DefResource` you never export is a perfectly legal **internal** resource — it
just has no boundary interface hung off it and lives entirely inside the guest.

The methods and statics travel *with* the resource block. **Free functions** that
pass handles around are ordinary [`Def`](./special-forms#def)s using the
`own`/`borrow` type spellings, and they are exported individually:

```wavelet
Export counter
Def make-counter Fn {start: u32} The counter counter(start)     // hands one out (own)
Export make-counter
Def bump-counter Fn {c: borrow(counter)} The u32 counter/next(c) // uses, doesn't consume
Export bump-counter
Def take-counter Fn {c: counter} The u32 counter/value(c)        // consumes (own)
Export take-counter
```

### Worked example: source to WIT

Putting the pieces together — the `counter` resource, exported alongside the three
free functions above:

```wavelet
Package "demo:counters@0.1.0"

DefResource counter {
  New:   Fn {start: u32} cell-new(start)
  next:  Fn {self: counter} The u32 Do [ cell-set(self add(cell-get(self) 1))
                                          cell-get(self) ]
  value: Fn {self: counter} The u32 cell-get(self)
  sum:   Static Fn {values: list(u32)} The counter counter(fold(add 0 values))
}

Export counter

Def make-counter Fn {start: u32} The counter counter(start)
Export make-counter
Def bump-counter Fn {c: borrow(counter)} The u32 counter/next(c)
Export bump-counter
Def take-counter Fn {c: counter} The u32 counter/value(c)
Export take-counter
```

synthesizes a world with a single `resource` block plus the three free functions,
each carrying its ownership mode straight into the WIT:

```wit
package demo:counters@0.1.0;

interface api {
  resource counter {
    constructor(start: u32);
    next: func() -> u32;
    value: func() -> u32;
    sum: static func(values: list<u32>) -> counter;
  }
  make-counter: func(start: u32) -> counter;
  bump-counter: func(c: borrow<counter>) -> u32;
  take-counter: func(c: counter) -> u32;
}

world counters {
  export api;
}
```

Note how each member role lowers: `New` becomes the anonymous `constructor`, the
instance methods become methods whose implicit receiver is the handle (so
`next: func() -> u32` — the `self` is the handle the method is called on, not a
parameter), and `sum` becomes a `static func` that returns the resource. The free
functions keep their `own`/`borrow` spellings (`c: counter` lowers to an owned
`counter`, `c: borrow<counter>` to a borrow).
