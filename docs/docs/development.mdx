Core WebAssembly instructions and Component Model contracts define runtime
semantics. Tests execute compiled components against explicit expected values and
traps. The execution corpus under `tests/fixtures/execution` has independently
specified expectations in `tests/fixtures/execution.json`, covering cell aliasing,
mutation order, recursion, compound values, bounds errors, and wrapping arithmetic.
The evaluator exists only for compile-time macro execution; it is not a runtime
reference implementation.

```console
./scripts/check.sh
```

Individual checks:

```console
cargo test
python3 scripts/check-quality.py
python3 scripts/check-duplication.py
python3 scripts/code-maat.py
cargo test --manifest-path tooling/wavelet-lsp/Cargo.toml
npm --prefix tooling/vscode run check
./scripts/regen-examples.sh
npm --prefix docs run build
```

## Structural and coverage gates

The quality gate checks formatting, Clippy diagnostics, function complexity,
and module size. A separate Lizard analyzer measures cyclomatic complexity
and non-comment function length; its pinned dependency installs automatically
into a private environment under `target/quality-venv`. No function may reach
1,000 code lines. New modules have a 1,000-line limit; existing large modules
and lint counts have checked-in upper bounds in `quality-baseline.json`.
Functions over 200 lines or cyclomatic complexity over 40 are reported;
Clippy also checks cognitive complexity against a threshold of 40.
The coverage gate runs the native suite with LLVM instrumentation and enforces
the minimum in `quality-coverage.json`.
These are migration limits for existing code, with no allowance for new lint
categories. After reducing debt, run
`python3 scripts/check-quality.py --update-baseline` and review the reduction.
Increasing a baseline requires an explicit reviewed change.

## Duplication

Copy/paste detection uses [jscpd](https://github.com/kucherenko/jscpd/blob/master/docs/rust.md)
5.4.3, pinned with its platform binaries in `tooling/quality/package-lock.json`.
The scan covers compiler and macro-evaluator Rust, language-server Rust, editor
JavaScript, and the docs implementation and example generator. It supports
TypeScript, JSX and TSX in those directories too. Generated WebAssembly
bindings, dependencies, build outputs, and separate test/fixture trees are
excluded; repeated test inputs do not represent duplicated implementation.
Clones must contain at least 10 lines and 100 tokens, ignoring whitespace and
comments. The gate rejects every new clone and every extra copy of an existing
clone using content fingerprints in `quality-duplication.json`; unrelated
new code cannot dilute a percentage to make a regression pass. Moving code
without changing its content does not require new exceptions.

Run `python3 scripts/check-duplication.py` locally; CI runs the same command.
The JSON report in `target/duplication/jscpd-report.json` contains both source
locations and the matching fragment for each clone. After consolidating shared
behavior, inspect that report, run
`python3 scripts/check-duplication.py --update-baseline`, and review the baseline
diff. Existing clones remain visible as refactoring work; accepting a new clone
requires a reviewed baseline change, not an increased percentage allowance.

## History analysis

[Code Maat](https://github.com/adamtornhill/code-maat) complements the source
checks with Git history evidence. `python3 scripts/code-maat.py` downloads the
official 1.0.4 standalone JAR and verifies its pinned SHA-256 on every run.
Install Java 17 first (`brew install openjdk@17` on macOS); the script recognizes
that Homebrew installation, `JAVA_HOME`, or Java on `PATH`. Git, Python 3 and
curl are also required. Download, checksum, parser, and execution failures are
reported as errors rather than skipped checks.

The default window is the 365 days ending at the HEAD commit date, capped at
1,000 non-merge commits reachable from HEAD. Override it with `--since YYYY-MM-DD`
and `--max-commits N`; `--repo PATH` selects another checkout. Shallow clones
are rejected with instructions to fetch complete history. CI uses a full-history
checkout and Java 17, runs fixture checks, and uploads the `code-maat-history`
artifact. The same report runs through `scripts/check.sh`.

Reports live in ignored `target/code-maat/reports`: `revisions.csv`,
`entity-churn.csv`, `coupling.csv`, and `hotspots.csv`, plus `summary.md`,
`metadata.json`, and the parser input `history.log`. Hotspot candidates are
current files ranked by revision count, then added/deleted lines, with their
current size shown separately; no synthetic quality score is assigned. Raw
reports retain historical files, including deleted paths. The metadata records
the exact commit, date range, commit cap, tool checksum, Java version, path
filters, and coupling criteria. Current sizes include working-tree edits;
commit metrics only reflect committed history.

The scope covers implementation and tooling paths, excluding generated wasm
bindings, separate test trees, dependencies, and build outputs. Inline historical
tests remain part of their original source files. Rename tracking is disabled
as required by the chosen `git2` log recipe; file moves can therefore split a
file's history. The input omits author identities, and no ownership or individual
contribution reports are generated. Coupling reports require at least five
revisions per file, five shared revisions, and 30% coupling; changesets with more
than 30 included files are excluded from coupling. These upstream evidence
filters are configurable in `tooling/quality/code-maat.json`.

History metrics are advisory review leads. A frequently changed file or a strongly
coupled pair does not fail the build: inspect the corresponding code and commits
to decide whether a refactor is useful. Bulk refactors, recent file moves, a small
sample, or a reached history cap can distort the ranking. Only failure to produce
a valid report fails the history-analysis job.

## Cross-language conformance

The integration and round-trip test workflows require `wasm-tools`,
`wasmtime`, `wac`, and `wkg` on `PATH`. The round-trip matrix also needs
`cargo-component` and the `wasm32-wasip1` Rust target:

```console
rustup target add wasm32-wasip1 wasm32-unknown-unknown
cargo install --locked cargo-component wac-cli wkg wasm-tools wasmtime-cli
cargo build
WAVELET="$PWD/target/debug/wavelet" conformance/wavelet/test-matrix.sh
```

The matrix checks both Rust seed implementations against Wavelet as caller and
callee, plus Wavelet against itself. See [Web applications](./web-apps) for HTTP
validation and deployment boundaries.

## Compiler and browser validation

The [Compiler API](./compiler-api) separates source/dependency inputs from host services. Compiler tests exercise in-memory projects, macro preparation, diagnostics, and snippet wrapping. Native and browser callers execute the returned components.

Runnable examples are authored in `docs/scripts/gen-examples.mjs` and generated into `docs/examples.json`. The generator compiles and executes snippets, with an explicit list of expected failures. Both native tests and browser playgrounds consume that data.

Multi-file playgrounds supply `sources`, an `entry` filename, and an `invocation` naming a zero-argument export that returns a string. Each file has its own editor; Run compiles the files together and displays the export's result. These project examples declare their expected results explicitly and are checked through native and browser execution. Examples may also declare explicit expected results directly in the generator.

Regenerate the examples after changing the language or examples:

```console
./scripts/regen-examples.sh
```

The script rebuilds the compiler component before regenerating results. The compiler artifact is committed so a documentation build requires only Node and npm dependencies.

Browser tests run the documentation examples and the commented language tour through the compiler component and execute the emitted artifacts. They also check error recovery and cancellation of a running component:

```console
npm --prefix docs run test:runtime
npm --prefix docs run build
npm --prefix docs run test:browser
```

Install the Playwright Chromium browser for the last command. The runtime unit tests also exercise worker cancellation, timeouts, dependency inputs, and the macro-host protocol.

## WAVE output compliance

`tests/wave_compliance.rs` feeds every documented result through the official
`wasm-wave` parser. The float and character backend vectors use that parser
too. Strings containing ASCII controls, including NUL, use WAVE Unicode escapes
and round-trip through both printers and the typed WAVE string parser.

One explicit ratcheted syntax exception remains: `tuple0()` prints `()`, which
WAVE does not accept. Unit still prints `{}`, the WAVE spelling of empty flags;
this is a diagnostic representation rather than a typed empty-record encoding.
Opaque functions and resources do not have a WAVE text serialization.

See the [resource state contract](./language/type-system#members-and-their-roles) for the supported representation shapes.
